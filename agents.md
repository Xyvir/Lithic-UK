# Missing Source Context (IMPORTANT)

**CRITICAL RULE FOR ALL AGENTS:**
If you need source context that is NOT available locally within this repository (such as vanilla TiddlyWiki core files or external third-party plugins), **DO NOT** attempt to find or download it yourself. Instead, you MUST explicitly **ASK THE USER (THE DEVELOPER)** to provide the relevant context manually. 

# Every Plugin Works Offline, From Inside the Wiki (CRITICAL)

**PHILOSOPHY:** Lithic is one portable file. A wiki must open and work with no network at all, on a USB stick, over `file://`, or on a machine that has never been online.

**REQUIREMENT:**
1. **No runtime loads from another host.** No plugin, widget, theme or library may fetch a script, stylesheet, font, model, or data file from a CDN or any other URL when the wiki runs. This includes `<script src>`, `<link>`, `@import`, `import()`, `fetch()` of a remote URL, and web fonts.
2. **Vendor every dependency into the repository.** Third-party code is either a pinned entry in `external.yml` (fetched at build time and bundled into the artifact) or a copy tracked under `wiki/local-plugins/`. Never leave a live external URL in a tiddler, and never rely on a host being reachable.
3. **Bundled means embedded.** The shipped artifact must carry every file it needs. Check this in the built output, not just the source, because a CDN URL can hide inside a minified bundle.
4. **A new plugin is judged by this first.** Before adding or keeping a plugin, confirm its assets are bundled and that it opens with the network disconnected. A plugin that cannot is not accepted until it is vendored.
5. **Approved exception: the ESP32 flash offer.** The launcher's Web Serial flash offer may fetch its firmware images (about 5 MB) from the project's GitHub at runtime, from the `esp32-firmware` branch (`raw.githubusercontent.com`) that `esp32-firmware.yml` replaces on every firmware build. Not from the release assets the same workflow publishes: GitHub answers a release download with a redirect to a storage host and neither hop sends an `Access-Control-Allow-Origin` header, so a page cannot read one however healthy the release is. This is the one permitted runtime load from another host, and it applies only to that offer. Nothing else in the launcher or the wiki may follow it, and the rest of the offline rules still hold.

# Do Not Watch CI/CD Runs (IMPORTANT)

**CONTEXT:**
Every push to `main` starts a release, and the developer monitors that pipeline personally. An agent that polls run status, conclusions, logs or artifacts after a push only reports what the developer is already reading, and it spends the session doing it.

**STANDARD OPERATING PROCEDURE:**
1. Push when asked, report the pushed commit, and stop there.
2. Do NOT query the GitHub Actions API, do NOT watch or summarize run status or conclusions, and do NOT re-fetch to check whether a release commit has landed.
3. Leave the pipeline entirely to the developer, who will pull the rebuilt artifacts when the release lands.

# Plugin Directory Map — Sources vs. Build Staging (IMPORTANT)

**CONTEXT:**
The wiki is assembled in CI from tracked sources. Knowing what is a tracked SOURCE vs. ephemeral BUILD STAGING is critical: editing staging is always wrong, and placing "live" content under staging/archive paths silently corrupts builds.

| Path | Role |
|---|---|
| `wiki/local-plugins/<name>/` | TRACKED SOURCE OF TRUTH for all Lithic-authored plugins/patches. **Edit here.** |
| `wiki/local-plugins/archive/` | TRACKED reference copies of RETIRED plugins. Never edit; excluded from builds by both `scripts/mirror.js` and `scripts/flatten-plugins.js`. |
| `vendored.yml` + `vendored-lock.json` | TRACKED manifest for libraries baked INTO a Lithic plugin ([pele](https://github.com/obsidianmd/pele) in `lithic-patch-mermaid`, `pdfjs-dist` in `lithic-import-handler`, `jspython-interpreter` in `tw-jspython`). `scripts/vendor-libraries.mjs` fetches each upstream at build time, twiki-izes it into the plugin's own `.tid` (front matter kept verbatim, body replaced, CRLF, no trailing newline) and records the version and hashes in the lock, so the repo's plugin is complete without a network. Unpinned entries follow upstream's latest release; `pin:` freezes one. The refresh runs BEFORE `mirror.js`, and the bytes it writes are committed on the release branch the same run opens, so they ride the existing review pull request. See **Vendored Libraries**. |
| `external.yml` + `external-lock.json` | TRACKED dependency manifest for third-party plugins (fetched fresh at build time). The lockfile caches REMOTE revisions (ETag/Last-Modified) only — the fetched artifacts in `wiki/external/` are gitignored, so `mirror.js` re-fetches any source whose local artifact is missing even when the lockfile matches. Includes the `flibbles/uglify` build-time compression tool (pinned via the same ETag mechanism). |
| `wiki/external/` | Gitignored MERGE CACHE: `external.yml` downloads with `wiki/local-plugins/*` copied over them. Regenerated by `npm run mirror` on every build. |
| `wiki/plugins/`, `wiki/themes/`, `wiki/tiddlers/` | GITIGNORED BUILD STAGING derived from the above by `scripts/flatten-plugins.js` (which wipes `wiki/plugins/` + `wiki/themes/` first, every run). Fully regenerable — **NEVER edit or commit**. |
| `wiki/tiddlywiki.info`, `wiki/output/`, `wiki/*.log` | Generated build config, artifacts, and logs. Not tracked. |
| `variants/` | TRACKED committed build variants NOT needed by the Tauri app (which bundles only `src/`): `prod.html` (plain-named copy of the uglified flagship, committed by release runs) and `pre.html` (legacy stale build — do not use for validation). Non-prod CI runs commit `variants/<env>.html`. |
| `src/launcher.html` | TRACKED **GENERATED** artifact — the shipped launcher, built from `launcher-ui/` by `scripts/build-launcher.mjs`. **Never hand-edit, and never publish a local build:** `npm run build:launcher` is a TEST, not the delivery path — it exists so you can run a launcher change and so `npm run check:push` has something to compare against. The committed bytes are produced by the release pipeline (`build-wiki.yml` runs `npm run build:launcher` and commits the result alongside the PWA bump), so a newer artifact arrives by PULL and never by hand. See **GENERATED ARTIFACTS ARE CI-ONLY** under *GitHub Actions Build Process*. It is the ONLY launcher artifact: the Tauri bundle (`tauri.conf.json`), the smoke/Puppeteer tests, the preview workflow, the server image and `autoupdate.sh` all reference this one name. `src/lithic.html` sits beside it as the engine it fetches. **Never gitignore it or `git rm --cached` it:** committing it IS publishing it — `deploy/autoupdate.sh` pulls this path from `raw.githubusercontent.com` on a timer to update running self-host instances, and `deploy/Dockerfile` `COPY`s it (a missing file fails the image build). Self-host has no build step at update time, so the committed file is its only delivery channel. |
| `assets/legacy-launcher.html` | TRACKED **ARCHIVE** of the retired hand-written launcher (the behavioral reference for the Svelte port). Read-only: `launcher-fragments/` is extracted from it and `scripts/inject-launcher-plugins.js` maintains its `defaultPlugins`. Not shipped anywhere. |

**STANDARD OPERATING PROCEDURE:**
1. To modify a Lithic plugin/patch, edit files under `wiki/local-plugins/<plugin>/` ONLY. Never edit `wiki/plugins/**` or `wiki/external/**` — both are regenerated from scratch at build time and any changes there are silently discarded.
2. If you ever find a Lithic-authored patch under `wiki/plugins/` (e.g. a "live" `lithic-patch-*`), STOP — that is either a stale artifact of a previous build or an archive leak. Fix the source under `wiki/local-plugins/` and delete the staging copy. Never `git add` anything under `wiki/plugins/`.
3. To RETIRE a plugin, MOVE it from `wiki/local-plugins/` into `wiki/local-plugins/archive/` and remove it from the `<env>-tiddlywiki.info` plugin lists. To revive it, move it back OUT of `archive/` and re-add to config — do not edit archived copies in place.
4. Third-party plugin updates happen via `external.yml` (+ `npm run mirror`), never by editing mirrored copies.
5. After adding/moving plugins, verify parity: run `node scripts/mirror.js && node scripts/flatten-plugins.js` and confirm the flatten manifest contains no `[SKIP]`/`[ERROR]` entries for your plugin.

# Vendored Libraries — Libraries Baked INTO a Plugin (IMPORTANT)

**CONTEXT:**
There are two shapes of third-party code in the wiki, and they are updated by two different mechanisms.

- **Third-party plugins** (`external.yml`) are fetched at build time into `wiki/external/`, a gitignored cache, and never live in the repo.
- **Libraries baked into a Lithic plugin** (`vendored.yml`) are twiki-ized into a `.tid` under `wiki/local-plugins/`, committed, and shipped inside the artifact, so the plugin is complete in the repo and the built wiki needs no network at all (see **Every Plugin Works Offline**).

Those baked-in files used to be pasted in by hand, which lost three facts: which upstream file they came from, which version they are, and whether the copy on disk still matches either. `vendored.yml` is that record and `scripts/vendor-libraries.mjs` is what keeps it true. It replaces only the BODY of the target tiddler: the front matter (`title`, `type`, `module-type`) is Lithic's description of the module and is never derived from upstream.

**STANDARD OPERATING PROCEDURE:**
1. **Commands.** `npm run vendor` refreshes every entry from upstream and rewrites its `.tid`; `npm run vendor:check` is the offline gate (does the body on disk hash to what `vendored-lock.json` says). Add `--dry-run` to fetch and transform without writing, `--only <name>` for one entry, `--pin <name=version>` to reproduce a specific version, `--summary <path>` for the markdown the workflow publishes, and `--best-effort` (CI only) so an unreachable registry keeps the repo's bytes instead of blocking a release. Wrong bytes always fail: a 404 for a pinned version, a missing file in the tarball, a tarball that does not match the registry's `integrity`, a body under `minBytes`, or a body missing an `expect` string.
2. **Adding a library** is four lines in `vendored.yml` (`name`, `package` + `file` or a `url`, `target`) plus the body's needs: `transform.replace` (each `from` must match, so an upstream rename fails the sync rather than silently doing nothing) and `transform.append` (how pele's browser-global build becomes a TW library module). Then `node scripts/vendor-libraries.mjs --adopt` records the bytes already in the repo, and the next refresh fills in the real version.
3. **Pinning is opt-in.** An entry with no `pin:` follows the registry's `dist-tags.latest` on every build, which is the point of the mechanism. An entry with `pin:` is frozen, and the pin is a deliberate decision:
   - **`pdfjs-dist` is pinned at 3.11.174 as a CEILING, not a bookmark.** Version 4 moved to `.mjs` builds and dropped `build/pdf.min.js`; `lithic-import-handler` loads a UMD global (`pdfjsLib`) as a TW library module and hands the worker tiddler its own copy of the worker script. Moving past 3.x is a migration of that plugin, not a version bump, and the two pdfjs entries must always carry the same version or the worker's message protocol drifts from the API it talks to.
   - **Never add `wiki/local-plugins/tw-react/` to `vendored.yml`.** `lithic-patch-whiteboard` is the consumer: that whiteboard is a decoupled TiddlyWiki port of an older, much smaller TLDraw, and React 19 is the runtime it was ported onto, so an automatic bump would move the runtime out from under the port. It stays hand-managed, on purpose: a React upgrade there is a whiteboard migration, never a version bump, and no weekly run may decide it.
   - **`tw-jspython`'s engine is the npm package `jspython-interpreter`, not `jspython`.** The package named `jspython` is an unrelated 0.0.3 by another author and ships no interpreter; the real project (github.com/jspython-dev/jspython) does not commit `dist/` either, so the npm tarball is the only place its browser build exists. That build is already UMD and takes the `exports`/`module` branch TiddlyWiki provides, so the entry needs no transform.
4. **Where it runs, and why there is no second pipeline.** The refresh is a step in `build-wiki.yml` (prod only, before `mirror.js`), and the same run already stages everything on a `release/<stamp>` branch and opens a review pull request, so the updated library and the artifact built from it arrive together in THAT review. `schedule:` adds a Monday tick (05:17 UTC) for the same workflow, which is the only reason the tick exists. It is prod only because a variant build ships the bytes committed on its branch, which is what makes a variant reproducible.
5. **After a pdfjs change, run the behavioural half by hand:** `npm run test:pdf-artifact [artifact]`. The text comparison in `check-pdf-plugin-unminified.mjs` proves the artifact carries the bundle; only the pixel test proves the import still renders pages. `scripts/vendor-libraries.mjs --check` runs in `npm run check:push`, so a vendored `.tid` edited by hand fails before it is pushed.

**WHAT THE MECHANISM ALREADY FOUND (2026-10-21):** the pdfjs bundles in the repo were **mojibake-damaged** (UTF-8 bytes read as Latin-1 and re-encoded, so `if (t[0] >= "ï")` had become `t[0] >= "Ã¯"`) and had lost pdfjs's `@licstart` licence banner somewhere in the paste. The refresh restores both: the body becomes upstream's UTF-8, banner included, at the same pinned version. Pele's vendored bytes, by contrast, reproduce EXACTLY from `pele@1.7.0 dist/pele.global.js` plus the appended export line, which is what proves the fetch → tar → CRLF → transform path is faithful rather than merely close.

**WHY (incident history):** an archive-leak bug (`mirror.js` copied `local-plugins/archive/` into `wiki/external/`, and `flatten-plugins.js` re-materialized it into `wiki/plugins/`) produced "live" shadow patches in the staging area, and stale mirror output (`wiki/plugins/D&DTools/` from a retired source) was nearly mistaken for tracked source. Fixed 2026-09; the archive guards + gitignore entries exist so this cannot recur.

# Tiddler File Format (`*.tid`)

**CONTEXT:**
TiddlyWiki parses `.tid` files and relies on specific formatting for headers and body content.

**PROBLEM:**
Including a trailing newline at the end of a plugin `*.tid` file can sometimes cause formatting or parsing issues within the wiki.

**STANDARD OPERATING PROCEDURE:**
When creating or editing plugin `*.tid` tiddlers, make sure that they DO NOT have a trailing newline after the last character of the body content. 
To guarantee this, after creating or editing a tiddler you should always execute the provided `trim.ps1` script, passing in the paths of the files you modified:
`powershell -ExecutionPolicy Bypass -File c:\Users\temp\Lithic_Dev\Lithic\assets\trim.ps1 -Files <path_to_file>`

Additional conventions: repo `.tid` files are **CRLF-encoded** — if your editing tool wrote LF, convert to CRLF first (see Environment & Workflow Notes). Pass **one path per `-Files` invocation**; the comma-joined multi-path form had `$_` quoting issues and silently did nothing.

**Bad Example (Trailing newline):**
```yaml
title: $:/config/lithic/sidebar-visibility/$:/core/ui/SideBar/More
type: text/vnd.tiddlywiki

hide\n
```

**Good Example (No trailing newline):**
```yaml
title: $:/config/lithic/sidebar-visibility/$:/core/ui/SideBar/More
type: text/vnd.tiddlywiki

hide
```

# Lithic Design Philosophy & Feature Integration Guidelines

**CONTEXT:**
Lithic is a highly opinionated, single-user PKMS. The following design decisions are intentional and should be respected when suggesting or implementing features. Do NOT suggest features that contradict these principles.

## Core Architecture: Streams-First Outliner

Lithic's primary authoring experience is built on the **Streams plugin** (outliner nodes), not the vanilla TiddlyWiki editor. Key implications:

1. **Keyboard navigation** (Tab/Shift+Tab indent, Alt+Up/Down reorder, Ctrl+Enter new sibling) is already part of the Streams experience. The vanilla Streams plugin is NOT in the local repo — it is fetched at build time via `external.yml` and extended by `lithic-patch-streams`.
2. **Full-text search** surfaces parent context via Streams' built-in breadcrumb navigation. This is not a gap.
3. **Per-tiddler version history** does not integrate well with Streams because Streams subverts the vanilla TW edit/draft workflow. Wiki-level versioning via git/GitHub and browser-storage backups in `launcher.html` is the chosen approach.

## Intentional Feature Omissions

These features have been deliberately rejected. Do NOT suggest or implement them:

- **Global graph view / force-directed backlink visualization:** Considered smoke and mirrors that conflates knowledgebase importance with size/complexity. The Pyramid sidebar (hierarchical mermaid tree) and backlink pills are sufficient for discovering connections.
- **Quick capture / inbox pattern / web clipper:** The developer believes that if an idea can be lost, it wasn't worth remembering. The interstitial journal (today's journal entry) is the only intended capture point — jot a quick note there and do a "full capture" later. Adding an inbox workflow adds friction under a false fear of losing ideas.
- **`$:/layout` in the document (`$:/layout` is intentionally NOT saved, and is NOT an edit):** which layout a Lith was last looked at in is view state, and an earlier round's request to persist it across a save has been withdrawn by the developer. Four writers set it on a press (the fullscreen whiteboard button, the whiteboard layout's own "Open In StoryView" button and rotate-gate exit, the streams row template's whiteboard action, and `pdf-open-request.js`), so a save that kept the tiddler rewrote the file on every view change, and a mount then opened in whichever layout the file happened to be saved with rather than the layout its engine ships. Both halves are therefore excluded, and they must stay in step: the dirty half is `wiki/local-plugins/lithic-core/$__config_SaverFilter.tid` (the wiki's own dirty-tracking filter — `SaverHandler.prototype.titleSyncFilter` in core — so a layout flip stops pulsing the save indicator, stops arming the beforeunload warning, and stops being recorded by `$:/lithic/startup/standalone-transient-recovery.js`, which compiles the same filter), and the save half is `wiki/local-plugins/lithic-save/save-all.tid` (`$:/core/save/all`: Save Wiki and the published monolith), `$:/lithic/exporter/lith` + `$:/lithic/exporters/export-to-new-wiki` (both export paths), and `LITHIC_BASE_FILTER` in `launcher-ui/src/legacy-saver.ts` (every `.lith` the launcher writes). A `.lith` that already carries a `$:/layout` still honours it on open — the value is read from the file, not ignored — it simply ages out, because no save writes it again. Do NOT re-add it to any of these filters, and do not treat its absence from a saved file as a bug. Do not edit `launcher-fragments/runtime.js` to match: that file is extracted verbatim from `assets/legacy-launcher.html` by `scripts/extract-launcher-fragments.mjs` and is a read-only archive, not shipped code.

## Feature Integration Guidelines

When adding new features to Lithic, follow these principles:

1. **FilterOps as the dashboard layer:** New "views" or "dashboards" (e.g., weekly review, orphan detection, overdue todos) should be delivered as **saved filters accessible via FilterOps**, not as standalone tiddlers or sidebar tabs. Users can use the existing "transcludify" / eyeball button to create permanent views from filters they find useful.
2. **External reference wiki for templates:** Anchor templates and example FilterOps presets should be delivered via an external "Lithic Reference Wiki" that users can drag-and-drop from, rather than bloating the core distribution.
3. **Markdown export via embed-stream:** Rather than building a dedicated markdown exporter, the strategy is to improve the `<<embed-stream>>` macro (removing extra whitespace) so it can produce markdown-friendly flattened output from nodestreams. This leverages existing workflows.
4. **Lightweight plugin integrations only:** When integrating third-party functionality (e.g., spaced repetition), prefer lightweight plugins that can slot into the Streams experience. Reject full "editions" or heavyweight solutions (e.g., TidMe) that would require architectural changes.
5. **Lithic Patina (simple UI mode)** will eventually hide advanced TiddlyWiki UI elements. Features gated behind Patina (like hiding alternate storyviews) should be designed as toggleable via config tiddlers, not hard-coded removals.
6. **Palette-derived contrast variables for dynamic theming:** Any feature needing palette-aware derived colors (Mermaid defaults, callout styling, charts) must consume the shared `--lithic-c-*` CSS variables instead of raw `<<colour>>` values or hardcoded hexes. They are computed with WCAG contrast math from the live palette by `$:/plugins/xyvir/lithic-core/contrast-publisher.js` (math primitives in `$:/plugins/xyvir/lithic-core/contrast.js`), re-publish automatically on palette switch, and carry a static `<<colour>>` fallback in `$:/plugins/xyvir/lithic-core/lithic-contrast.css`. Roles: `surface, page, foreground, foreground-muted, node-bg, node-fg, node-border, line, cluster-bg, cluster-border, cluster-fg, note-bg, note-fg, note-border, accent, accent-fg, scale-1..8, dark, code-bg, code-border, code-fg, code-ref, code-accent, code-warn, code-select-bg, code-select-fg, caret, menu-bg, menu-fg, menu-muted, menu-hover-bg, menu-hover-fg, menu-border, menu-selected-fg, notify-bg, notify-fg` (each also as `-rgb` triple and `-alpha-12/-alpha-25` tints). `code-*` covers editor/code surfaces (keywords/strings/numbers map to `code-accent`/`code-ref`/`code-warn`, accents are hue-locked via `hueShift` from `dirty-indicator`/`primary` so the brand hue survives); `menu-*` covers popup/context menus (hover band may be slid toward the surface when mid-luminance primaries make 4.5:1 ink unreachable); `notify-*` is the palette's OWN `notification-background`/`message-foreground` pair with a contrast-locked ink, shared with the streams patch's highlight band so the context-menu target band cannot drift from it -- bind such bands to `notify-*`, never to a hardcoded hex or to `menu-hover-*`. To add a new derived role, extend the `derive()` role map in the library — consumers pick it up automatically. Note that palette tiddlers are dictionary-type: read them via `getTiddlerData`, and they may contain intra-palette `<<colour x>>` references that must resolve recursively (palette's own entry always wins over Vanilla, whether value or reference).

**CSS variables in stylesheets — always use `type: text/css`:** stylesheets that consume `var(--lithic-c-*)` must be typed `text/css` and must NOT embed `<<colour ...>>` macros inside `var()` fallbacks. TW's `text/vnd.tiddlywiki` parser mangles CSS custom-property double-hyphens into en-dashes at render time (the dash rule), which silently kills every `var(...)` declaration, and it also parses `<<` inside CSS comments as broken macros. Sheets that still need `<<colour>>` transclusion (e.g. palette-key fallbacks unrelated to vars) must stay `text/vnd.tiddlywiki` — but then keep `--` out of CSS custom properties and `<<>>` out of comments. A wikitext sheet that needs BOTH macros and `var()` has a third option: disable just the dash rule (`\rules except dash`) so the double hyphens survive, which is what `$:/lithic/streams/styles/ctx-preview` does. Prefer the exclusion form over `\rules only <list>`: a list must name every pragma the sheet uses (`macrodef`, `whitespace`, ...), and the first unrecognised pragma ends the scan. That is the trap behind the dash exclusion too -- TW only recognises pragmas in the sheet's LEADING block (`parsePragmas()` bails at the first non-pragma content), so a CSS comment or any text placed above a `\define` leaves the definition unparsed and leaks a literal `\end` token into the emitted CSS, silently killing the next selector. Keep every pragma above all comments and text.
7. **Author-declared diagram styling is authoritative:** when a diagram or widget declares its own styling (Mermaid `%%{init}` directives, `style`/`classDef` statements, per-widget attributes), default theming must stand down rather than compete on CSS specificity. The mermaid wrapper tags self-styled containers `mm-user` and default rules are scoped to `:not(.mm-user)`.

8. **Hardcoded colour gate (`scripts/check-colors.js`, runs in CI before anything is built):** any colour literal in `wiki/local-plugins/` outside the script's `ALLOWLIST` fails the build. Use `<<colour field>>` in wikitext (inline styles and `<style>` blocks) and `var(--lithic-c-*)` in `text/css` sheets. For alpha washes prefer the publisher's companions -- `rgba(var(--lithic-c-foreground-rgb), 0.22)` or the pre-faded `var(--lithic-c-notify-bg-alpha-12)` -- over grey/black/white literals, and remember that muting often needs no colour at all (a completed row is `opacity: 0.6`, not `color: gray`). Comments that mention colours are reported as informational and never fail. Allowlist entries each carry a reason and are deliberately narrow: palette definitions, the print stylesheet and the mermaid media-print block (paper is white), vendored single-line bundles, and content defaults that must NOT follow the wiki palette (PDF.js rendering, the 3D model material, the text-file iframe, whiteboard paste). Run `node scripts/check-colors.js --verbose` to see them. A new exception needs a reason that would survive review, and a line-level exception (a `box-shadow` neutral, say) beats a file-wide one.

9. **Offline gate (`scripts/check-launcher-offline.mjs`, runs in the launcher build CI step and in `npm run check:push`):** the launcher is one file that has to behave the same on an instance, on a USB stick and over `file://`, so nothing in it may load from somebody else's host. The gate fails on any external `src`/`href`/`@import`/`url(...)` -- no allowlist for loads, because no version of this app needs one -- and on any absolute http(s) URL whose host is not declared with a reason in the script's `EXTERNAL` list, which is how a new endpoint becomes a decision rather than an accident. `--browser` adds a runtime pass: boot the artifact over `file://` with every non-local request aborted, drive search and the new-Lith entry, and fail if anything was attempted. That is the only way to judge a host assembled at runtime (`'https://' + host`), so the two passes are not redundant. `node scripts/check-launcher-offline.mjs --list` prints every URL with its declaration for review. Declared today: w3.org namespaces, Svelte's own error links, the GitHub and lithic.uk anchors a person clicks, the two swarm endpoints (`docs/swarm.json` and `intro.lith` for the ephemeral public coderunner widget, both of which fail quietly offline), and the bookmark field's placeholder.

10. **Launcher palette (`launcher-ui/src/color-palette.ts`, guarded by `launcher-ui/src/color-palette.test.ts`):** every colour the launcher draws is declared once, in that module, and reaches the page as a custom property: `paletteCss()` renders the `:root` block `styles.css` carries between its `lithic-palette:` markers, so the sheet holds no colour of its own and there is exactly one copy of every value. Edit the palette, run `npm run palette` to rewrite the block, and commit the two together. Washes are derived rather than written: `WASHES` names a colour and an alpha and the serializer computes the `rgb()` from the two, so recolouring `accent` moves all three of its washes with it, where a hand-written `rgba(138, 180, 248, 0.12)` is correct only until somebody changes the blue. The alphas are a ladder, not a recording: a tint behind text is 12 or 20 percent, a banner 10 or 45, a shadow 30, 50 or 72, a wash over chrome 7. **One ramp per job** is the rule that keeps the palette small: a job gets one tone, a new tone has to be a job the palette does not already have, and where several tones did one job the winner is the one the sheet used most and it keeps the role name. The test fails on a stale block, on a colour literal anywhere under `launcher-ui/src` (comments included, the way the dash sweep counts them), on a variable the sheet reads and the block does not define, on two tokens holding the same colour, and on two tones in one family closer than 8/255 apart, which is the distance at which they are one tone: the fix is to merge into the nearer, never to add a value. A 60 token ceiling (`PALETTE_TOKEN_CEILING`) is the ratchet that stops the recording growing back. `launcher-ui/index.html` is deliberately out of scope, since its `theme-color` is a decision about browser chrome rather than about the launcher's own drawing: no part of this reads or writes that file. The canvas that paints an instance icon does read the palette (`paletteValue('surface.control')`), because a canvas takes a colour string rather than a custom property. In prose the sheet names a colour by token (`line.thumb` over `surface.panel`), never by hex, because the hex is the thing that moves. **The consolidation pass (2026-09-30):** the first pass was a faithful naming of what the sheet held, 271 literals and 25 washes named as 113 tokens, and what it held was 93 hex tones picked by eye at different times: twelve secondary text greys between `#a0a0a0` and `#bcbcbc`, two ambers six units apart doing the same job, five pale ambers all meaning "amber ink on an amber banner". The second pass holds the same rule as the rest of this file and came out at 53 tokens (40 colours, 13 washes), with no redesign: every survivor is a tone the sheet already drew, the hues are untouched, and 116 of the sheet's colour values moved, in 64 shifts, the largest 57/255. Three are above 40 and the rest are below 31: `ok.base` takes the tick's `#4caf50` so a green check is drawn in the launcher's own green (57, the one merge plainly visible on screen), while `ok.rim` takes a badge border and `danger.soft` a salmon hover that had drifted from their own families. Evidence for a retune is produced rather than asserted, by resolving both sheets and listing every declaration whose colour moved with its distance, plus a headless comparison of the built artifact's computed colours; that is how the numbers above were measured, and how a future merge should be judged before it is committed.

11. **Every OS-specific behaviour is one capability with one implementation per platform (`src-tauri/src/platform/`):** the Svelte launcher is *one* artifact shipped to every desktop, so it cannot branch on the operating system without shipping every platform's vocabulary to every user; what it branches on instead is **capability**, which Rust answers. `platform/mod.rs` is the table: `Os`, `current()`, `capabilities()`, and one routed function per capability (`install_dir`, `install_target`, `running_image`, `launched_from_install`, `program_dir`, `state_dir`, `open_in_browser`, `flash_browser`, `reveal`, `install_launch_entry`, `register_file_associations`, `make_launchable`), each answered by `windows.rs`, `linux.rs` or `macos.rs` under the same name. Adding a platform is a file and a table row, never an `if` in `lib.rs`, and the command `platform_capabilities` is how the page asks rather than guesses. `flash_browser` is the one capability about another program rather than the platform: the flash offer flashes in its own dialog where the window's webview implements Web Serial, and hands the same `src/launcher.html` to a Chromium browser at `?flash=1` (written to a temporary file) where it does not. A current WebView2 does implement it, measured: it answers `navigator.serial` and draws its own chooser, titled "tauri.localhost wants to connect to a serial port", so the handoff exists for WKWebView, WebKitGTK and an older WebView2 rather than as the desktop app's only route. **The Linux and macOS modules are compiled on every platform, on purpose:** the Windows implementations are the only ones that need a platform crate (COM, the registry, ShellExecuteW), and the local gate runs on the developer's Windows machine, so code inside `#[cfg(not(windows))]` is code `cargo check`, `clippy` and `cargo test` never see. Keeping them unconditional is what makes the local gate type-check, lint and unit-test the Linux path (the `find_icon`, desktop-entry, `exec_path` and install-target rules all have tests that run on Windows); only the FFI bodies in `windows.rs` are conditional, and the two modules carry `#![cfg_attr(windows, allow(dead_code))]` for the same reason `instance_search.rs` carries the mirror-image attribute. **What `capabilities()` means for the page:** an Install offer exists only where `install` is true, the offer's sentence is keyed on the `launch_entry` **token** (`start-menu` | `application-menu` | none) rather than on a noun, because the noun is a translation and the platform cannot know the language any more than the page can know the platform; and the three webview flags are the flag side of the `#[cfg(windows)]` hooks in `webview_auth`, `instance_search::read_caches` and `instance_copy::forget`, with a unit test that fails when one is implemented and its flag is not moved with it. **macOS reports `install: false` deliberately:** a Mac distribution is a `.dmg` holding `Lithic.app` beside a link to `/Applications`, so the drag *is* the install, the file types are the bundle's `Info.plist`, and `open -R` is the reveal; an app that also copied its own bundle into `~/Documents` would be a second copy in a folder the user did not choose. **And the one rule macOS cannot keep is "beside the program", which is why that question is routed rather than a call to `current_exe`:** a Mac program is a *bundle*, so the executable's folder is `Lithic.app/Contents/MacOS`, inside the app — state written there is state the next install replaces (a cask upgrade swaps the whole bundle, a hand-dragged newer copy does the same), it is not something a signed bundle will accept, and a quarantined run is translocated to a read-only path where the writes fail anyway. So `program_dir` answers with the folder *holding* the bundle (found by walking up to the `.app` rather than by counting Tauri's layout, so a `cargo run` from a checkout keeps the plain rule) and `state_dir` — the folder the portable sidecar and the vault live in — answers beside that folder when the bundle is somewhere a copy is carried (a stick, a folder of one's own, Downloads) and `~/Library/Application Support/Lithic` when it is parked in an `Applications` folder, or when the folder it sits in cannot be written at all (a read-only mounted image, a translocated copy). Both are asked once per process, because the sidecar's writers ask on every command and a probe file is not something to leave on somebody's Desktop repeatedly. **The concession stops at the platform line:** Windows and Linux keep the executable's own folder, unchanged and unconditional, because there it is a real folder that travels — the program, its state and the liths beside it are one portable neighbourhood, and no part of macOS' bundle arithmetic is allowed to reach them. **Linux installs itself properly, which is the part Windows code could not do:** `install_launch_entry` writes one freedesktop entry to `$XDG_DATA_HOME/applications` (which is also the file-association registration, since a `.desktop` file declares the MIME types it opens), copies the AppImage's own icon into the icon theme rather than pointing at a path inside a temporary mount, and marks the copied program executable. Three Linux-specific facts are load-bearing: `$APPIMAGE` outranks `current_exe` (`platform::running_image`), because the executable inside an AppImage's mount is gone at the next reboot and copying or byte-comparing it would be copying a ghost; the install target keeps the `.AppImage` extension, or the kernel stops treating the copy as one; and an `Exec=` path containing a space has to be quoted the way the format specifies, which is the difference between a menu entry and a menu entry that does nothing. **And the installed copy is not content of the folder it lands in:** that folder is also where a first backup proposes to live, so both distributions write the installed file's own name into its `.gitignore` before the copy arrives (`ignore_installed_copy`, in `shim/src/install.rs` and in `install_monolith`), because the alternative is a 4 MB binary in somebody's wiki history and in every clone of it. The two implementations do not link each other, so each carries its own test and a harness runs them over the same inputs to hold them in step. **And the offer is not a second installer:** `platform::package_managed` answers whether something other than this app placed the copy that is running, from a sandbox marker (flatpak, snap) or from a path under a root the system owns (`Program Files`, `%LOCALAPPDATA%\Programs`, `/usr`, `/opt`, `/nix/store`, `/snap`, `/var/lib/flatpak`, `/Applications`), and `install_supported` makes that lose to the platform's answer, so a `deb`, `winget` or `brew` copy is offered no Install button and no hand-delivered update while the manager stays its updater. The install *record* outranks the path evidence, because `%LOCALAPPDATA%\Programs` is both winget's per-user default and this app's own fallback when there is no Documents folder, and `launched_from_install` is the only thing that tells those two apart. The update half needs no second check: it is gated on that same record, which no manager's copy can satisfy. The rule is unit-tested including its boundary cases (`/usrfoo` is not under `/usr`, `C:\ProgramFiles2` is not under `C:\Program Files`) and both sandboxes, and the comparison folds case on Windows and macOS but not on Linux, because it has to judge a Windows path on a Linux runner.

12. **Monkey inputs are a local instrument, never a gate (`scripts/monkey-launcher.mjs`, `npm run monkey:launcher`):** the launcher's entry boxes are fuzzed on demand, by a person, because a fuzz run is noisy by nature — it needs a browser, it is driven by a seed — and a red build on an unlucky seed teaches people to press retry rather than to fix the crash it found. What it finds is promoted into `scripts/test-puppeteer-launcher.mjs`, which is the harness CI runs, and `scripts/pre-push-check.mjs` fails if any workflow names it. **What it does:** it discovers every entry box the page draws by walking `input`/`textarea`/`contenteditable` inside each dialog it can open, keyed on the class names a person's clicks reach (never on a copy string, so a translation cannot hide a box), collapses a six-box PIN into one field, opens the collapsed advanced section of the backup dialog, and reopens the surface for each value instead of clearing it, because a field that keeps state across a close is its own finding. **What it can judge:** that the document is still the launcher, that typed markup did not become markup (a mutation watcher plus a `__monkeyPwned` bait flag), that the × still closed the dialog, that a key storm left no overlay Escape could not clear, and that nothing reached the network — every non-local request is aborted, so a mount cannot quietly fetch the published engine and replace the page mid-run. **What it cannot:** anything a Rust command does with a value, which is why the harness says so in its own report rather than implying coverage. **The five checks it pins** are the guardrails a person would state out loud — a name already in Recents marks the check invalid and typing past it clears the mark, a name the launcher has to change says which file it will create, a `javascript:` address is refused and not stored, a PIN of symbols neither fills nor submits, an empty name still starts a document and the page survives the mount failing over `file://` — and they run after the fuzz pass, because they are only worth keeping if they still hold once the same dialogs have been stirred. `--strict` also fails on the `GAP` findings. The one class its first run found — a control character (a line break, a tab, a NUL) surviving `normalizeLithName` into the name — is now stripped rather than refused, in `normalizeDocumentName` (C0 and DEL removed, both ends trimmed, an empty result still `untitled`), because the character is an accident and a name is not the place to reject a request; `document-format.test.ts` names the three and `legacy-saver.test.ts` pins the launcher's own path through it. Names are also held to Windows' filename rules, because Windows is the strictest of the three systems this launcher ships to and a name legal there is legal on macOS and Linux as well: a run of `< > : " / \ | ? *` becomes one hyphen (so `MP3/FLAC notes` keeps its boundary and `../../etc/passwd` becomes a name in the folder rather than a walk out of it), trailing spaces and dots go the way Windows would drop them, a reserved device name (`CON`, `NUL`, `COM1`, `CONIN$`, and their superscript spellings) is moved out of the way with a leading underscore because `CON.lith` is the console with a suffix rather than a file, and the stem is cut so the whole name fits the 255-character component limit without halving an emoji. The report's separator column is therefore an inverted assertion: a separator surviving means the rule was weakened, not that a value was unlucky. **And the rewrite is never silent.** Every rule that makes a name legal somewhere also merges two names into one (`a/b` and `a-b` both arrive as `a-b.lith`, `CON` and `_CON` likewise), which is unavoidable once one system's rules are the baseline but must not be invisible: the New Blank Lith field draws `copy.newLith.renamed` above itself whenever the name that will be written differs from the name that was typed, and says nothing for an ordinary name so the notice stays worth reading. `typedDocumentName` in `document-format.ts` is the comparison it is drawn from (the typed name plus the extension, sanitized by nothing), `document-format.test.ts` pins both halves (silent for `notes`, `My Notes`, `notes.lith`; speaking for `a/b`, `notes.`, `CON`, a `.html` name and a 400-character one), the collision check the field already had reads the same normalized name, so the second document to arrive under a merged name reports itself as taken, and `test-puppeteer-launcher.mjs` asserts the notice at phone width, where it wraps inside the field rather than sliding under the page edge. `--list` prints what would be fuzzed and stops, which is what to run after adding a field. **Opening is the other half (`--mounts`, `--no-drop`, `--no-payload-urls`, `--mount-timeout`):** a Lith is bytes, and bytes do not arrive through a box. The opening phases serve the artifact, the engine beside it and a dozen fixtures from one loopback origin for the length of the run, because a `file://` page cannot fetch a sibling engine and a refused fetch would make every mount read as broken, then open each fixture three ways: through the Mount button with `showOpenFilePicker` answered from that origin, by dispatching a real `drop` event carrying a `File` (the bytes the OS would hand over), and through the launcher's own `?json=` address. The fixtures are the shapes an opened document has: empty, delimiters only, no title, duplicate titles, a title that is markup, a title full of filter brackets, NUL, ESC and DEL in a body, random bytes read as text, a body holding `<script>` and an image handler, one 8 MB tiddler, two thousand small ones, and a seeded mutation of a valid Lith, which is what an interrupted write leaves. **What it can judge:** the page ends as the wiki or as the launcher and never blank; a well-formed Lith always boots, or the pass says out loud that the rest of it proves nothing; an engine that boots into a document that draws nothing is a failure rather than a pass, which is also why the boot check asks for `$tw.wiki.getTiddlerText` instead of for `$tw.wiki` (a broken store leaves a half-built `$tw` behind, and that object was being mistaken for a wiki); payload markup reaching script is a failure; and a press or a mount that moves the address is a note, because a bookmark row hands the window to its instance on purpose, where a launcher that vanishes at the same address is the wedge. `--mounts=all` opens every fixture, a number samples that many from the seed, and `off` skips the phase. **Two harness faults had to be cleared before those phases could say anything, and both were the harness lying rather than the launcher failing:** a local helper named `URL` shadowed the constructor the fixture server needed, so it answered 400 to every request and the phase reported that the launcher would not come back, and the Tauri stand-in (which answers every command with `null`) made the served page take the desktop route into a mount that quietly did nothing, which is why the phases now install the instrumentation with `bridge: false` and fuzz the browser launcher they are actually driving. A phase that cannot finish is a finding and a note, never an uncaught error: the report is the whole point, and a reload that will not land must not take it down. **The class it found is the one a text box can never reach:** a tiddler body containing `</script>` was spliced into the engine's `application/json` store raw, which closed the element early, truncated the store, and booted a wiki with no page around it (a note about HTML, or a plugin's own docs, is enough to hit it). `storeJson` in `launcher-ui/src/legacy-launcher-runtime.ts` writes `<` as a JSON unicode escape through `String.raw`, so the six characters survive the source and the body parses back unchanged, and `legacy-launcher-runtime.test.ts` pins a store that carries `</script>`, `<script>` and `<!--` without gaining a second script element. The `script-body` fixture is what caught it, and it now renders in 913 ms where it used to report `booted blank` at 256 ms. **The edges a person reaches by accident are their own phase (`edge` rows in the report):** a picker answered by cancellation, and one that throws into the classic chooser (the `busy` flag has to come back off in both, or the Mount control stays disabled for the rest of the session); an engine that answers 404 at every candidate, which has to say so and stay usable; an engine that takes 25 seconds, where the page has to still be the launcher while it waits and Escape has to work before the answer arrives; a gesture carrying three documents, one of them twice, where the repeated titles are refused with a note rather than queued as duplicate rows and a row's own ✕ removes only that row; opening a Lith that already holds a queued title, which asks before the merge replaces the stored copy and, when accepted, has to land the queued copy in the wiki; a `?url=` payload fetched and carried into the wiki; a real clipboard paste and an IME composition, judged the way a field always is; a thousand rows and a hundred-kilobyte query, whose timing is reported rather than asserted because no budget for it has been decided; and a cache whose writes are refused, where the mount still has to boot. `clickMount` waits for the control to be enabled before pressing, because a press into a disabled button is dropped and the phase then blames the launcher for a mount that never happened. **And the mutation generator, not a new seed, is where new bytes come from:** each run draws one to three edits and the report names them (`truncated at half, then every delimiter doubled, then tabs where the blank lines were`), because a hundred seeds of one shallow edit produced a hundred near-identical files. The slow engine makes a full run about half a minute longer, which is the price of the one thing that cannot be tested quickly.

**CONTEXT:**
The launcher explains itself through the UI, not through prose. Every string a user can read — modal text, tooltips, button labels, status lines, empty states, Rust-side `detail` strings — follows one rule:

**One short sentence. 10-15 words. No em dashes. Nothing restated.**

1. **Terse and curt.** The icon, the row and the button label already carry the meaning; the sentence orients the user to what the UI is for, and stops. If a sentence needs "which means that", either it is too long or the UI is unclear.
2. **Non-technical.** No git, cache, index, token or file-format vocabulary unless the user has to act on it. "Saves push to GitHub automatically." beats "Every save of a file in this folder commits and pushes to main." **One entry in a Lith is a note**, never the engine's own word for it: the queue's rows name their titles, and a sentence about a merge says "note" where a count or a class of thing has to be named, so the wiki vocabulary never reaches a person. `copy.test.ts` walks every deck leaf, and the source of every sentence function, failing on a word that has been decided against (`tiddler`, `TiddlyWiki`, `wiki`, `payload`, `serialization`, `engine`, each read from a stem so a plural or a compound is caught, and in every language a deck is written in), which is what keeps a new dialog from reintroducing the word that was just removed. `cache` is deliberately not on that list: a handful of strings say where a saved copy actually is, and a person can act on it.
3. **No em dashes or en dashes.** They read as editorializing, wrap badly in tooltips and modals, and are the single clearest sign a string was written by an agent rather than trimmed by hand. Use a period, or rewrite. The ban covers comments and test names as much as copy, which is what makes it checkable: the launcher's sources are swept clean of both dashes and `scripts/check-launcher-copy.mjs` scans them absolutely, so nobody has to work out which dash in a built artifact was a shipped string.
4. **No restatement.** State the consequence once. A warning names what is happening and what the button will do — not why, and not twice.
5. **Mechanics live in `README.md`.** The launcher is meant to be understood without explanation; anyone who wants the machinery reads the README, never a modal.
6. **Diagnostics are data, not prose.** A raw error string appended after a short clause is fine: `Last save did not upload: not authorized`. Do not editorialize around it.
7. **Both sides of the bridge count.** Rust `detail` strings render in the sync dialog, so they obey the same rule and stay word-for-word in step with the matching entry in `launcher-ui/src/git-sync-health.ts` (`healthFailure`). The same fault must not read two different ways depending on where the user looks.
8. **The language comes from the environment, and only a request or a pin overrides it.** Which deck a page reads is decided once, at import, by `resolveLocale` in `launcher-ui/src/copy.ts`, in this order: `?lang=es` (a request, and the escape hatch from everything below it), then `VITE_LAUNCHER_LOCALE` (the artifact's own pin, compiled in), then the person's own languages (`navigator.languages`, which is the environment in all three shapes of the launcher at once: the published PWA reads the browser, an instance's launcher reads the same browser, and the desktop app reads the machine, since the webview it runs in is the machine's own), then `en`. A request nobody can carry is refused rather than trusted, so a misspelled link reads as the shipped language. **A pin is forced, not preferred**, which is what lets one build be a language site, and `?lang=` is the way out of it. A self-hosted instance pins without rebuilding by setting `LITHIC_LOCALE`, which rewrites the two files that belong to a deployment rather than to the release (`deploy/pin-launcher-locale.sh`, checked by `scripts/check-self-host-locale.mjs`): the redirector that sends `/` on to the launcher, which then brings `?lang=es` for a visit that brought no query of its own, and the install manifest's start URL. Language is the document's as well as its words: `main.ts` publishes the resolved locale as `document.documentElement.lang`, and every date the launcher draws formats with the same tag, or a screen reader, a spell-checker and a timestamp each disagree with the page.

Worked examples:

| Too long | Terse |
| --- | --- |
| "Rebuilding drops it and deletes its cached copy and history. Files on disk are untouched." | "3 liths have no file on disk, so rebuilding deletes their cached copies and history." |
| "Every download is a complete, working copy of the wiki as it was at that moment — your history is never modified." | "Downloads are complete copies. This wiki is never changed." |
| "Pick the icon this instance is known by. It becomes the browser tab, taskbar and phone-home-screen icon, so your instances stay distinguishable at a glance." | "This icon identifies the instance in your tab and taskbar." |

When a string has to carry a count, a filename or a timestamp, keep those as data and let the sentence stay short; do not grow the prose to accommodate them.

## Launcher Modal Affordances: One Dismiss Per Dialog

**CONTEXT:**
Every launcher modal that can be dismissed carries an × in its corner (`.modal-close`). A Cancel button beside it that runs the same handler is a second control for one function, and it takes the place of the decisions the dialog actually exists to make.

**RULE:**
1. **No Cancel where the × does the same thing.** Delete it; do not relabel it. The dialog may then have no action row at all — the per-instance PIN prompt is deliberately in that shape, because the sixth character is the submit and the × is the way out — and that is the target, not a gap to fill.
2. **A "cancel" that is not the × is named for what it does.** The GitHub device flow's button abandons the authorization being waited on and leaves the dialog open where the × closes it, so it reads `Stop waiting`. The inline control in the sync progress line stops a transfer mid-flight, so it reads `Stop syncing`, never `Cancel`.
3. **A yes/no confirmation keeps its Cancel instead of a ×**, because there both answers are decisions and neither is a dismissal: the rebuild confirmation (Cancel is the choice not to drop the rows it just listed) and the destructive confirm. Every other dialog gets the × — including the ones whose Cancel was its only dismissal beside real choices, like the session-collision prompt, whose two buttons are the ways to open and whose Cancel meant not opening at all.
4. **Nothing else beside the × dismisses, whatever it is called.** A `Close`/`Done` that was a dialog's only action is the same function under a friendlier word, so it goes with the Cancels: the vault manager's empty and list shapes now carry no dismissal, and a shape with nothing to decide has no action row at all (the empty manager is title, one line, and the path). git-sync's connected view keeps only `Reconnect` and `Disconnect`. One dialog has neither a × nor a Cancel and is left as it is: the three-way unsaved-edits prompt, whose three answers are policies about the edits rather than a way out of the dialog — the one place left to settle by hand.

**ENFORCEMENT:**
the rule is stated at `.modal-close` in `launcher-ui/src/styles.css`, and `assertNoExtraDismiss` in `scripts/test-puppeteer-launcher.mjs` fails when a dialog that owns a × carries a button whose whole label is `Cancel`. Call it for each new dialog the smoke test opens, and keep the sheet's action rows read from `ui-gallery/copy-deck.md` when trimming one.

## Launcher Status Line: Every Line Has a Deadline

**CONTEXT:**
The header's status line holds the last thing the launcher said, and a later sentence replaces an earlier one. That half is right: a control's own answer should stand until the next thing happens. What was missing is an end. `status` has **64 writers** in `launcher-ui/src/App.svelte`, and exactly **two** of them ever retire their own sentence — the install confirmation, and `reportAndRetire`, whose comment already explains why that one had to: a pass that runs behind a dialog has no click to follow it, so its line and the animated dots beside it stood for the rest of the session, reading as indexing that never stopped. Every other writer sets something final and leaves, and the render site then always drew `.activity-dots`, which mean *work in progress*. So a finished action pulsed forever. Reported from the shipped app as "sometimes these status messages get stuck and linger", with a screenshot of `Mounted <file>.lith` still waving long after the mount.

**RULE — a status is transient by definition:**
1. **One deadline per line, measured from the moment it was written.** At **15s** the line is gone on its own. It first shipped with two moments, the dots stopping at 15s and the sentence staying until 45s, and against the real launcher that read as a line that had half finished going away, so the second stage was removed: a line is either saying something or it is gone. The threshold *is* the contract, so it is exported from `launcher-ui/src/status-lifetime.ts` and asserted in the test beside it: a line may stand at least 10s and never more than 60s. A minute is the outside of "transient" and a blink is not a status, and those two assertions are what fail on the day somebody moves the number quietly.
2. **It is a catch-all on purpose, not a fix per writer.** Every writer that forgets to retire its line is a new bug and there are dozens of them, where one deadline is one place to be right. A writer that knows its sentence is worth reading twice keeps using `reportAndRetire`: assign `status`, then retire it on your own timer, guarded by the text you wrote. The cost this accepts is named rather than hidden, and the second half of the rule is the answer to it: a clock cannot tell a success from a failure, so a line that names something to act on opts out of the clear (rule 5) instead of a reader having to hope it was still on screen.
3. **Assigning `status` arming its own deadline is not optional.** One reactive statement (`$: syncStatusDeadlines(status, heldStatus)`) arms the clear or the hold, a newer line cancels the older line's deadline, and the clear is guarded by the text, so an older line's deadline arriving late can never take away a newer sentence. Anything that writes `status` gets the deadline for its class, which is exactly the point: nothing has to remember.
4. **What stopping looks like, and who it is for.** `.activity-dots.settled i { animation: none; }` in `launcher-ui/src/styles.css`, the same static shape the `prefers-reduced-motion` rule already gives these dots. It draws only for a held line now, because an ordinary line's dots leave with the sentence; a held line's sentence, its colour and its place are untouched.
5. **A line that names something to act on is held, and is never cleared on a clock.** `reportHeld(message)` in `App.svelte` is how a writer says so: the line keeps the deadline's settle half alone, so the dots stop at 15s and the sentence then stands until the next thing replaces it. Five copy entries are held today, at eleven sites: `openFailed` (four: the disk picker, a recent row, a disk path, and an instance opened externally), `blankLithFailed` (two), `noPath` (three), `noCachedCopy`, and the `copyDropNote` failure. Held by the sentence rather than by a flag, so an ordinary writer that runs after a failure cannot inherit the exemption. **The stopping is what makes the exemption safe rather than a hole in the rule:** the bug this whole section exists for was an unending pulse reading "work in progress", and a standing sentence is not that. `mountError` and `remoteError` are the same class in their own element, where there are no dots to stop, and they have always stood this way; the failures that reach them (`uploadFailed`, `listingFailed`, `openNameFailed`, `createFailed`, `deleteFailed`, `downloadFailed`, `reindexFailed`, `introFailed`, `payloadFailed`, `droppedInvalid`) need no change for the same reason.

**ENFORCEMENT:**
`launcher-ui/src/status-lifetime.ts` holds the threshold and the arming, and `status-lifetime.test.ts` holds the 10s floor, the 60s ceiling, that an ordinary line arms one deadline and goes at it with nothing left armed, that cancelling a line gives its deadline back, and that a held line arms one deadline, settles once and wakes no second time. The behaviour belongs on the running component rather than in the timers alone, and the technique is worth keeping: with `window.showOpenFilePicker` replaced in the page by handles that answer `getFile`, a multi-file `Mount a Lith` reaches `copy.status.added(n)`, which mounts nothing, so a status line can be produced and watched at leisure, where every other status reachable in a browser is followed by a mount that replaces the document and takes the line with it. Measured that way for the two-moment version (see the round log): written with `animationName: status-wave`, settled 15.2s later with the sentence still on screen, cleared 45.0s after the write, and a newer line arriving after the previous one had settled came back with the animation running again. The hold was measured the same way, with a pick whose second `getFile` rejects so the real Mount button reports `copy.status.openFailed`: 275 consecutive samples carried that sentence from t=0.2s to t=55s, still on screen and static at 45.4s and 50.0s, and the ordinary line that replaced it at 55s cleared **44,999ms** after its own write, which is the half that proves the exemption does not leak to the line after it. # What is a `*.lith` File?
A `.lith` file is an extension of the vanilla TiddlyWiki `*.tid` file format, which is based on an HTTP RFC format for headers and body.

**Key differences and requirements for `.lith` formats:**
1. It supports multiple tiddlers appended together within a single file.
2. The **triple-asterism** (`⁂⁂⁂`) is used as a strict delimiter to separate each individual tiddler inside the file. Do NOT use standard asterisks.
3. The `title` field is explicitly required for each tiddler entry within the file.
4. The `created:` and `modified:` front matter items are not necessary and should be omitted to save space.

# GitHub Actions Build Process

**CONTEXT:**
The Lithic PKMS wiki is compiled and published automatically via a GitHub Actions CI/CD pipeline (`.github/workflows/build-wiki.yml`).

**PROCESS OVERVIEW:**
1. **Dependency Installation:** The pipeline starts by setting up the Node.js environment and running `npm install`.
2. **Refreshing Vendored Libraries:** Before anything is mirrored, `node scripts/vendor-libraries.mjs` refreshes the libraries baked into Lithic plugins from `vendored.yml` (prod only, so a variant build ships its branch's bytes). It runs before the mirror step because the mirror copies `wiki/local-plugins/` over the fetched tree: a library refreshed afterwards would be baked into nothing. The rewritten `.tid` files and `vendored-lock.json` are committed on the release branch, so the updated library and the artifact built from it are reviewed together. See **Vendored Libraries**.
3. **Mirroring External Plugins:** It dynamically fetches all third-party dependencies defined in `external.yml` using `npm run mirror`. The mirror step then copies the tracked Lithic plugins from `wiki/local-plugins/` (minus `archive/`) over the fetched tree in `wiki/external/`. **Never place "live" plugins directly in `wiki/external/`** — it is a merge cache, not a source location.
   - *Note on External Plugins:* External plugins (such as `tiddlystudy`, `relink`, etc.) are intentionally omitted from the repository itself to keep the source tree clean and ensure they are fetched fresh or from specified remote sources during build time.
4. **Flattening:** `scripts/flatten-plugins.js` reads `plugin.info` titles out of `wiki/external/` and re-derives the clean staging trees `wiki/plugins/` + `wiki/themes/` (wiping both first, every run). Retired content under `archive/` is explicitly skipped so it cannot leak into builds. It writes `wiki/flatten-manifest.log` — check it for `[SKIP]`/`[ERROR]` entries when adding plugins.
5. **Configuration Generation:** It dynamically generates the TiddlyWiki build configuration (e.g., `prod-tiddlywiki.info`) representing the specific compilation target.
6. **Compilation:** The core `tiddlywiki` CLI is invoked to compile the output. For prod builds, the flibbles/uglify plugin is loaded and engaged via `npx tiddlywiki wiki --uglify --build index`, minifying core/plugin JS/CSS and the plugin JSON stores (~26% size reduction, 10.7 MB -> ~7.93 MB). Non-prod builds run plain `--build index` (generate-config.js strips flibbles/uglify from the pre/dev merged configs).
   - *Uglify purge:* the tracked local plugin `wiki/local-plugins/lithic-save/` overrides the `$:/core/save/all` shadow with a save filter that hard-excludes `$:/plugins/flibbles/uglify` (and the wizard plugin) from the published store — the CLI equivalent of the uglify wizard's 'purge uglify-related tiddlers' option, so the uglify engine (~1 MB with its bundled library) never ships inside the artifact. Render-time `publishFilter` variables do NOT reach the core shadow macro on core 5.4.1 (verified), which is why the override plugin exists.
   - **The wikitext uglifier is DISABLED, deliberately** (`wiki/local-plugins/lithic-default-configs/$__config_flibbles_uglify_text_vnd.tiddlywiki.tid`, value `no`). Only JS/CSS/JSON compression runs. Reason (field-tested 2026-09-21): the wikitext pass collapses load-bearing whitespace - it eats the space between SVG attributes and after macro parameters (`\parameters (size:"22pt")` -> `\parameters(size:"22pt")`, `width=<<size>> height=<<size>>` -> `width=<<size>>height=<<size>>`), so all ~115 `$:/core/images/*` SVGs become one malformed attribute run. A malformed `<svg ...>` swallows the following content as SVG child nodes, which browsers never paint - that is why the ahanniga context menu rendered as an empty themed box. It also shifts every slashcommand `caret-pos` (the `$:/lithic/slashcommands/*` bodies lost their spaces), which is the `/wb-image` caret regression. Measured damage: 894 tiddler texts differ vs a plain build (98-99 whitespace-only). Cost of disabling it: +140 KB (7.79 MB -> 7.93 MB, still ~26% below plain). Do NOT 'fix' the SVGs by hardening the tiddlers - the source tiddlers are already correct; only the build mangled them.
   - **The PDF import plugin is EXCLUDED from the uglify pass** (`wiki/local-plugins/lithic-default-configs/$__config_flibbles_uglify_blacklist.tiddlywiki.tid`, a `$:/config/flibbles/uglify/blacklist` list of the plugin's three tiddlers). `lithic-import-handler` carries its own pdfjs-dist build, which terser had already minified, and re-minifying that with the bundled uglify-js is what turned every imported PDF page white from `build-2026.09.16-1658` onward: the import still reported success and wrote a whiteboard, and text extraction kept working, so only the pixels said anything was wrong. Bisected between the two 2026-09-16 releases by swapping single unminified tiddler texts back into the bad artifact and measuring the rendered pixels: restoring `pdf.js` alone restored every page (0% ink at 255 mean without it, 3-20% ink with it), while the widget, the worker and the handler each changed nothing. Cost of the exclusion: +147 KB on the 8.11 MB artifact (1.8%), measured by building the same tree twice, with and without the config tiddler, and diffing the stored tiddler texts: the plugin's own bundle is the only text that changes between the two builds. **The blacklist matches an exact title, and these titles are not the plugin's `plugin.info` title** (the tiddlers are `$:/plugins/lithic/lithic-import-handler/*` inside the bundle `$:/plugins/xyvir/lithic-import-handler`), so `scripts/check-pdf-plugin-unminified.mjs` asserts the built artifact still carries each of them byte-for-byte (line endings normalized) and runs in the prod verify step of `build-wiki.yml`: a renamed tiddler, a lost config tiddler or a changed uglify setting fails the build here rather than in somebody's whiteboard. `scripts/test-pdf-import-artifact.mjs` is the behavioural half (`npm run test:pdf-artifact [artifact] [--pdf file]`): it drops `scripts/fixtures/pdf-import-smoke.pdf` on a real artifact in headless Chrome and requires ink on every rendered page, and the same tree built without the blacklist fails it at 0% ink on every page. Do NOT harden the plugin's sources against minification, and never 'fix' a re-minified bundle by editing the artifact.
7. **Post-Processing & Release:** The built HTML file is renamed, branded ("Lithic PKMS"), and for production releases, the PWA manifest/offline service worker version is bumped. Prod builds commit BOTH `src/lithic.html` (uglified flagship; consumed by the Tauri app, the launcher engine path, the PWA service worker, and build-server.yml) AND `variants/prod.html` (an identical plain-named copy for download). Non-prod builds commit `variants/<env>.html`. The final artifacts are committed to a `release/<stamp>` branch and opened as a review pull request, and are attached to a GitHub Release when that pull request is merged — the flagship as ONE asset named `lithic.html` (taken from `src/lithic.html`, so the download is the same bytes the app embeds), beside `launcher.html`, `wiki.zip` and `flatten-manifest.log`. There is no light build in the release: the light export is generated on the fly by the launcher, so no `lithic-light.html` is committed or attached. It used to attach the flagship twice, as `lith.html` and as the identical `prod.html`, which read as two artifacts that were the same file; `variants/prod.html` is still committed, it is just not a release asset any more. The FOUR DESKTOP distributions are attached by the chained job instead (`.github/workflows/desktop-release.yaml`, run by `publish-release.yml` as `build-desktop`, after the merge): `Lithic_<MM.DD.YY-HHMM>.exe` for Windows, two macOS downloads (below), and two Linux AppImages whose names state which engine each carries, because their sizes differ by a factor of forty and the name is the only thing a downloader sees before the download. `Lithic-webgtk_<MM.DD.YY-HHMM>.AppImage` bundles WebKitGTK plus JavaScriptCore, about 43.5 MB of its 82 MB, and a name that hid that would make the 82 MB look like a mistake. `Lithic_<MM.DD.YY-HHMM>.AppImage` is the shim (`shim/`, assembled by `scripts/build-shim-appimage.sh`), which links no toolkit at all and serves the launcher and the engine to the browser already on the machine: the name reserved for it on 2026-09-30, now taken. **Both Linux AppImages are published, and the 82 MB one is not redundancy to be tidied away:** the AppImage catalogue (appimage.github.io) lists an application by opening one AppImage from its newest release and requiring it to draw a window of its own, which a build that serves a page to a browser cannot do, and its picker refuses to guess when one release carries two AppImages it cannot tell apart. So the WebKitGTK build is what that catalogue can carry, the shim stays the Linux distribution, and the two names are what keep them apart. All of them are stamp-named so the downloads of one release are distinguishable at a glance, and the stamp rule is shared with the exe. **The macOS job publishes two files rather than one, and Gatekeeper is the whole reason.** The disk image (`Lithic_<MM.DD.YY-HHMM>.dmg`, built `--target universal-apple-darwin` with both rustup targets named, because one download has to open on either Mac) is the shape a Mac installs from; the tarred bundle (`Lithic_<MM.DD.YY-HHMM>_universal.app.tar.gz`) is the same app as one file, and it is not redundancy, because nothing fetches it through a browser: `curl` writes no quarantine attribute, so it is the one macOS download with no Gatekeeper step in front of it, and unpacking it anywhere is the whole install. Neither is signed or notarized — a Developer ID and the notarization it enables are a paid annual membership — so a browser-fetched image needs one trip through System Settings → Privacy & Security → Open Anyway. That same decision is why the Homebrew cask lives in the project's own tap (`Xyvir/homebrew-tap`, `brew install --cask xyvir/tap/lithic`) rather than in homebrew-cask, whose casks must be signed and notarized; the tap is in the tap's own repository on purpose, because a workflow's token cannot write to another repository, so the tap *pulls*: a scheduled job there reads the newest release that carries an image, writes the cask from that asset's stamp and checksum, and commits it. The `macos-15` runner is pinned for the same reason the Linux jobs pin 22.04 — the label decides the toolchain that produces a release — and it does not raise the artifact's floor: Tauri sets the bundle's own deployment target (10.13 by default, untouched here). The jobs are separate on purpose, so a failure in one costs only its own platform. The AppImage is built on `ubuntu-22.04` rather than `ubuntu-latest` because an AppImage links against the build machine's glibc: a 24.04 base raises the floor to glibc 2.39 and the artifact then refuses to open on Ubuntu 22.04 and Debian 12. That runner is deprecated (retirement 2027-04-17), so the migration is a 22.04 container on `ubuntu-latest`, never a newer runner.

8. **The launcher UI gallery is the review material.** A `deck` job in `build-wiki.yml` shoots `scripts/ui-gallery.mjs` against the launcher the build just produced. It needs four things the build job does not have, and the workflow says so by name: Node 24 (the deck imports `launcher-ui/src/color-palette.ts` directly, which is type stripping), a Chrome for Puppeteer, ImageMagick 7 for the tiling, and a text font for the tiling to be legible. The middle two are `scripts/install-imagemagick7.sh`, which fetches the project's own AppImage rather than the distro's packages: `ubuntu-24.04` runners carry no ImageMagick at all, and `apt install imagemagick` stops at version 6, which has no `magick` entry point for the deck to invoke. The font is the script's other job, for a reason worth knowing: montage asks freetype for its label's *metrics* before it lays anything out, so a machine with no font fails the tile outright rather than drawing an unlabelled sheet, and removing `-label` does not avoid it. The image's own package list has one font, an emoji face, and the AppImage bundles neither a font nor a fontconfig of its own, so `scripts/sheet-tile.mjs` names a font by path and tiles with `+append`/`-append` when there is none to name. The contact sheets are force-pushed to the `ui-deck` branch as a single commit under `deck/<stamp>/`, and `scripts/gallery-pr-body.mjs` composes the pull request body out of the deck's own `ui-gallery/sheets.json` and `ui-gallery/modal-coverage.md`, embedding every sheet by raw URL. They are referenced by URL and never committed because `ui-gallery/` is gitignored on purpose: 18 MB of PNGs is not a thing to put in the history of the branch under review. The job is `continue-on-error` by design rather than as a softener: the deck is review material and not a gate, so a pane that cannot reach its state (which fails `ui-gallery.mjs` on purpose, so a sheet cannot silently become a picture of the wrong thing) must not stop a release from being reviewable at all. The pull request opens either way, and its description says the pictures are missing.

9. **Every setup step that repeats across jobs is one definition under `$/.github/actions/`, and a step with two copies is a step that drifts.** `setup` (checkout, Node, the npm cache) was already that; this pass added `rust` (the toolchain plus `swatinem/rust-cache`, with the cached workspace and the rustup targets as inputs) for the six jobs that compile Rust, and `linux-deps` (the apt list as an input, with the downloads kept across runs) for the three that install system packages, and `browser` for the two that drive one. The copies had drifted before they were merged: `rust-check.yml` installed its toolchain *before* its cache while all four desktop jobs did it the other way round, which is two orders for one pair of steps and nothing in either file to say which is right. Two rules come with a composite: a `run:` step inside one MUST name its `shell` (there is no default shell to inherit), and a new action is referenced the way `setup` already is here, `$/.github/actions/<name>`.
   - **The icon set is committed, so regenerating it changes nothing.** `src-tauri/icons/**` is tracked and pixel-identical to what `npm run tauri icon src/app-icon.json` writes (measured 2026-10-16: all sixteen files compared pixel by pixel, no differing pixel, only the encoder's bytes, the fresh set slightly smaller), so the four jobs that each regenerated the set per release were overwriting the committed art with itself and rewriting sixteen tracked files apiece. Only `android-release.yml` still generates, and not by oversight: `scripts/patch-android.mjs` copies `src-tauri/icons/android/**`, which no commit carries. Run that command by hand when `src/app-icon.png` changes, and commit what it writes.
   - **A job that never drives a browser does not download one.** `npm ci` installs puppeteer, whose install step fetches Chrome unless `PUPPETEER_SKIP_DOWNLOAD` is set (the browser cache this checkout's own runs filled is 681 MB). `desktop-release.yaml`, `android-release.yml`, `publish-release.yml` and `build-wiki.yml` now set it at the top, and the skip covers the whole file. The only two jobs in the pipeline that drive a browser are `build-launcher.yml`'s smoke suite and `build-wiki.yml`'s `deck`, and each gets one from `$/.github/actions/browser`, which caches it: the install line the two were sharing, called where it has to run (after the job's `npm ci`, because the command is the repository's own puppeteer), so a repeat run restores the browser instead of fetching it. A browser-needing job added to one of those four files installs one through that action.

**HOW THE WIKI ARTIFACT GETS REBUILT (IMPORTANT):** `build-wiki.yml` **builds on push and stages a review**. A push to `main` that changes anything load-bearing runs the prod build and commits `src/lithic.html`, `variants/prod.html`, the rebuilt `src/launcher.html` and the PWA bump, but on a `release/<stamp>` branch rather than on `main`, and then opens a pull request carrying them. Merging that pull request is what publishes: `.github/workflows/publish-release.yml` fires on the `src/lithic.html` the merge lands, tags the build, creates the GitHub Release and chains the desktop and server jobs. **Those chained jobs read the committed `src/lithic.html` rather than downloading anything:** an artifact belongs to the run that uploaded it, and `built-wiki` is uploaded by this build run while the installers run in the publish-release one, so the two `continue-on-error` steps that used to sit in each job could never resolve and would only have replaced the committed file with a copy of itself (this build copies `wiki/output/lith.html` onto `src/lithic.html` before committing and uploads that same file). They were removed from all six jobs on 2026-10-16; do not restore a download in their place. Closing the pull request publishes nothing and leaves nothing to undo, because no tag and no release exist yet to clean up. That one path is the trigger because only a release writes it and `build-wiki.yml` deliberately ignores it as an output, which is what stops a merge from starting another build **when the release carried nothing but artifacts**. It does not cover a release that carried the vendored refresh: `vendored-lock.json` and the `wiki/local-plugins/` body are live paths a hand edit must still rebuild, so the merge of PR #87 (which landed both) rebuilt an identical tree and opened PR #88, whose only diff was the PWA bump. That is the cycle the `landing` job in `build-wiki.yml` answers, from the push's own commit subjects rather than from a path list: `Release build-<stamp>` and `Merge pull request #N from <owner>/release/<stamp>` commits mean main just received the build this pipeline already reviewed, so nothing is rebuilt and no deck or pull request is opened, while a dispatch, the weekly tick and any unparsable payload still build. `checkReleaseTrigger` in `scripts/pre-push-check.mjs` fails if that wiring is dropped. Nobody dispatches a release. **The cost of the gate is one delay worth naming:** `deploy/autoupdate.sh` pulls `src/launcher.html` from `main` on a timer, so a launcher fix now reaches a self-hosted instance when somebody merges its review pull request rather than when the build finishes, and a pull request left open leaves that timer serving the previous launcher. Its filter is a blacklist over `**`: out are docs, CI config, the local-only harness and the paths the release commits itself, so a wiki-source edit (any `.tid` under `wiki/local-plugins/`) or a `launcher-ui/src/**` edit reaches the review pull request with the push, not whenever a human remembers to dispatch. Dispatch is still how you get the other configs (`pre`/`dev`/`all`) and a dry run, and it is the only way to run an edit to the workflow itself, since `.github/**` is excluded. `build-launcher.yml` is still a manual preview run. (Until 2026-09-23 `bump-pwa-version.yml` fired on any push touching `src/lithic.html` or `src/launcher.html` and committed its own version bump; it is manual now, because a prod release bumps the PWA itself and an unattended writer to `main` is what rejected a release's final push — see the policy block below. Automatic releases came back deliberately on 2026-09-24, once the local gates that verify the tip being pushed — `scripts/pre-push-check.mjs` (launcher-ui tests, svelte-check, cargo check/clippy/test), the Puppeteer smoke, the offline gate — were in place: hand-dispatching was the answer to an unverified `main`, and that is no longer the situation.) Do **not** rebuild `src/lithic.html` locally and commit it: the JSON key order inside the plugin bundles follows the host filesystem's directory order, so a Windows build differs from the Ubuntu runner's in key order alone (same 48 tiddlers, every individual tiddler hashing identically, ~19 bundles affected). The artifact the launcher ships is separately verified by `npm run check:push`, which fails when a fresh Vite build differs from the committed `src/launcher.html`.

**GENERATED ARTIFACTS ARE CI-ONLY (IMPORTANT):**

**CONTEXT:** `src/lithic.html`, `src/launcher.html` and `variants/*.html` are build OUTPUT, committed only because the repository itself is their delivery channel: `deploy/autoupdate.sh` pulls `src/launcher.html` from `raw.githubusercontent.com` on a timer, `deploy/Dockerfile` `COPY`s it, and the Tauri bundle embeds it. Nothing on the receiving end builds, so the committed bytes ARE the shipped bytes.

**POLICY — a local build is a test, never a release:**
1. `npm run build:launcher` (and a local `tiddlywiki --build index`) exist so you can run and inspect a change against the shipped shape. Treat whatever they write as scratch output.
2. **Never commit or push a locally built artifact.** If a local build is sitting in your tree when you go to commit something else, `git checkout -- src/launcher.html src/lithic.html` first — a stray local build swept into an unrelated commit is how the artifact drifts from its sources.
3. **To get a newer artifact, PULL it** (`git pull`, or `git checkout src/launcher.html`) after the release lands. Do not manufacture one locally to catch up.
4. If you changed `launcher-ui/src/**` or anything under `wiki/local-plugins/`, say so when handing the change over: the release starts itself when the push lands, so a stale committed artifact is the normal state only for the minutes between that push and the run it triggered — `git pull` when it lands, and never manufacture the artifact by hand.

**WHY (incident history, 2026-09-23):** the browser-storage fallback had to reach deployed instances, and with no release in flight the only route was a hand-built `src/launcher.html` plus a hand-pushed PWA bump — precisely the reflex this policy ends. Within the hour a prod release, dispatched to do that job properly, died at its FINAL push: `main` had moved while the build ran (an unrelated commit), `git push` was rejected, and because that commit exists only on the runner, the rebuilt artifacts, the tag, the GitHub Release and the `build-tauri`/`build-server` jobs went with it. Two separate lessons — nothing should be pushed while a release is building, and the artifact never needed to be built locally in the first place. Both are now mitigated mechanically: `build-wiki.yml` and `bump-pwa-version.yml` share a repo-wide `concurrency: group: main-writers` (two writers now serialize instead of racing), and every CI push to `main` goes through `scripts/ci-push-main.sh`, which retries onto the new tip rather than letting one rejected push discard a finished release. That retry no longer covers a prod release, which stages its commit on a branch and is therefore never rejected; it now covers the non-prod variant commits and `bump-pwa-version.yml`.

**KNOWN GAP (do not be misled by it):** `npm run check:push` → `scripts/check-launcher-artifact.mjs` still FAILS when the committed `src/launcher.html` differs from a fresh local build, and its failure text still says to commit that build (`git add src/launcher.html && git commit`). That advice is obsolete under this policy and is the loudest reason local builds still get published: a change under `launcher-ui/src/**` CANNOT satisfy the gate without one, because CI can only regenerate the artifact once the source is on `main`. Do not follow it. The gate should warn instead (or skip while `launcher-ui/src/**` is being changed) and has not been changed yet; until it is, a launcher-source push that the gate blocks is the one legitimate use of `git push --no-verify` — and a cheaper call now that the same push starts the release which regenerates the artifact: `--no-verify` skips the gate, not the release.

**IMPORTANT DIRECTORY RULES:**
- **`wiki/plugins/`, `wiki/themes/`, `wiki/tiddlers/`, `wiki/external/` are ephemeral build staging (all gitignored)** — regenerated from scratch on every build. NEVER edit or commit anything there; all edits belong in the tracked sources: `wiki/local-plugins/<plugin>/` (Lithic plugins), `external.yml` (third-party deps), and the `<env>-tiddlywiki.info` configs. See the **Plugin Directory Map** section near the top of this file.
- The items within the `assets/` directory are merely for **local reference** and debugging. They should **NOT** be manually edited. The CI/CD pipeline dynamically handles fetching the definitive external dependencies based on `external.yml` during the build process.
- The `TIDDLYWIKI_PLUGIN_PATH`/`TIDDLYWIKI_THEME_PATH` env vars in `.github/workflows/build-wiki.yml` point at the staging dirs `wiki/` + `wiki/plugins` — they exist only so the CLI can load the flattened plugins at compile time. **Local builds MUST set them too** (e.g. `TIDDLYWIKI_PLUGIN_PATH="$PWD/wiki:$PWD/wiki/plugins" TIDDLYWIKI_THEME_PATH="$PWD/wiki/themes" npx tiddlywiki wiki --build index`): without them the CLI silently builds from core plugins only, producing a tiny (~3.8 MB), plugin-less `index.html` that looks like a successful build.

# TiddlyWiki JS Plugin File Format (`*.js.tid`)

**CONTEXT:**
When creating or editing JavaScript plugins, macros, or startup modules in TiddlyWiki via `.js.tid` files, the boot parser requires a specific dual-header format to function correctly. 

**PROBLEM:**
If a `.js.tid` file is missing the leading plain-text frontmatter, or missing the `/*\` comment block, the TiddlyWiki boot sequence will crash with a `Syntax error in boot module` or `Unexpected identifier` error. The core `$tw.boot` system reads the `/*\` block to extract module metadata *before* the main parser is loaded.

**STANDARD OPERATING PROCEDURE:**
Every `.js.tid` file MUST contain the module metadata **twice**:
1. Once as plain-text tiddler fields at the very top of the file (e.g. `title: ...`, `type: ...`, `module-type: ...`).
2. A second time inside a `/*\` ... `\*/` block comment immediately preceding the JavaScript code.

*(Note: The `created:` and `modified:` fields are not necessary and should be omitted from both the plain-text headers and the comment block metadata).*

**Example Format:**
```javascript
title: $:/Lithic/Widgets/example.js
type: application/javascript
module-type: widget
```

# Custom Filter Tiddlers (FilterOps & Advanced Search)

**CONTEXT:**
The user relies on a custom TiddlyTools filter dropdown UI (referred to as `FilterOps`) for quickly accessing saved filters.

**PROBLEM:**
If you create a custom saved filter and place it in a standard namespace (e.g., `$:/lithic/Filters/...`), it will show up in the default Advanced Search but **will not** appear in the FilterOps dropdown. The dropdown explicitly looks for a specific TiddlyTools prefix to build its menu.

**STANDARD OPERATING PROCEDURE:**
When creating or modifying saved filter tiddlers that are meant to be quickly accessible by the user, you MUST place them within the TiddlyTools namespace so they integrate with the custom UI automatically.

1. **Title Prefix**: Must start exactly with `$:/config/TiddlyTools/Filters/`
   - Example: `title: $:/config/TiddlyTools/Filters/All Highlights`
2. **Tags**: Must be tagged with `$:/tags/Filter`
3. **Description**: Include a `description` field which is what will be displayed in the dropdown menu.
   - Example: `description: All Highlights`
4. **Filter**: The actual filter logic goes in the `filter` field.

**Example Tiddler (`*.tid`):**
```yaml
title: $:/config/TiddlyTools/Filters/My Custom Filter
tags: $:/tags/Filter
description: My Custom Filter
filter: [tag[SomeTag]] -[is[system]]
```



# `.lith` Importer / Exporter Type Quirk

**CONTEXT:**
The `.lith` deserializer/importer (`register-lith-extension.js`) automatically injects `type: text/markdown` into any non-system tiddler that lacks an explicit `type` field during import. 

**QUIRK / EDGE CASE:**
The `.lith` exporter does **not** have symmetric logic to strip this out or explicitly mark native `vnd.tiddlywiki` types. This was an intentional decision to keep the exporter lightweight.
As a result, if a standard TiddlyWiki tiddler (which implicitly defaults to `vnd.tiddlywiki`) is exported to a `.lith` file, it will be exported without a type field. If that same file is subsequently re-imported, the importer will catch it as a "no-type non-system tiddler" and erroneously convert its type to `text/markdown`.

**STANDARD OPERATING PROCEDURE:**
If you encounter weird formatting issues where standard tiddlers suddenly behave like markdown after being passed through a `.lith` export/import cycle, be aware of this asymmetrical behavior. Do not try to "fix" the exporter with heavy JS macros unless explicitly requested again.

# `.lith` Exporter Rules (`$:/lithic/exporter/lith`)

**CONTEXT:** the in-wiki exporter is what the scratch editor's "output to `.lith`" workflow runs. Each rule below is the reverse of a bug that shipped, all re-verified headlessly against a real engine (5.4.1).

1. **Render the block in the exporter; never transclude `$:/core/templates/tid-tiddler`.** That template's text *begins with a newline*, so every block it renders — the first included — opens with a blank line. The parser then took that blank line as the field separator, swallowed the field section into the body, and produced a tiddler with no title, which the engine will not boot around: the file white-screened on mount and looked corrupted rather than off by one newline. `parseLithToJSON` now skips leading blank lines too (defence in depth), but the emit side renders fields and text itself so its bytes match `serializeJsonToLith` exactly (bar the `.tid` file's own trailing newline). Two traps: the `$name$: $value$` separator inside the `template` attribute must be a REAL newline (a literal `\n` escape is not decoded there, and ships `tags: x\ntitle: y` as one line), and the separator goes *between* blocks (`<$reveal default=<<counter-last>>`), never before the first, so nothing can lead the file.
2. **Exclusions must name a source: `-[all[tiddlers+shadows]prefix[x]]`, never `-[prefix[x]]`.** A `-` run whose content is a bare prefix operator is re-evaluated as a *source*, and source operators only see real tiddlers — so everything the engine contributes as a shadow (themes, core, plugin bundles) survived it. Measured on the shipped build: `-[prefix[$:/themes]]` removed 3 of 63 theme tiddlers, `-[prefix[$:/core]]` removed 0 of 871; the sourced form removed all of each. The exported file is mounted *on top of* `lithic.html`, so a stale baseline copy in a `.lith` overwrites the current engine tiddler — this is a correctness bug, not just bloat.
3. **The filename comes from the active query, never the word "tiddlers".** The `filename` field finds the saved query whose `filter` matches `exportFilter` and uses its `description`, sanitised with `splitregexp[\s+]join[_]`, falling back to `export`. A saved query is a `$:/config/TiddlyTools/Filters/<Name>` tiddler holding the filter in a **field** (`get[filter]`, not its text); match with `field:filter<exportFilter>` (a literal operand cannot contain `[`/`]` and errors with "Missing [ in filter expression"). `replace[...]` returned nothing in this build — `splitregexp`+`join` works.

**SCOPE:** the exclusions cover what the launcher injects (`~`-prefixed overrides, `$:/plugins/lithic/ephemeral/*`, `$:/config/OfficialPluginLibrary`) plus the engine and session classes the `.lith` save path already drops (boot, core, themes, temp, state, HistoryList, `$:/StoryList`). Plugin *roots* are deliberately kept, so a plugin the user installed into their wiki still round-trips.

# Syntax Highlighting for Custom Codeblocks (`highlight.js`)

**CONTEXT:**
TiddlyWiki's core `HighlightPlugin` uses the `$:/config/HighlightPlugin/LanguageMappings` dictionary to map Tiddler *MIME types* (e.g., `text/x-python`) to languages for rendering entire tiddlers. 
However, this config dictionary DOES NOT map the identifiers used in Markdown-style codeblocks (e.g., ` ```jspython `).

**PROBLEM:**
If you try to alias a custom codeblock language like `jspython` to `python` by adding it to `$:/config/HighlightPlugin/LanguageMappings`, the core widget will not recognize it and the codeblock will not be highlighted.

**STANDARD OPERATING PROCEDURE:**
To register new codeblock languages or aliases so that ` ```customlang ` is properly styled, you must do it programmatically by hooking into the `highlight.js` engine on startup. 
Create or modify a TiddlyWiki JS startup module (like `wikitext-highlighter.js.tid`) and call `hljs.registerLanguage` or `hljs.registerAliases` directly on the `hljs` object:
```javascript
var hljs = window.hljs || require("$:/plugins/tiddlywiki/highlight/highlight.js");
if (hljs && typeof hljs.registerAliases === "function") {
    hljs.registerAliases('customlang', {languageName: 'existinglang'});
}
```

# TiddlyWiki Macro Pragmas (`\define`)

**CONTEXT:**
TiddlyWiki parses files from top to bottom. Macro definitions (`\define`) and other pragmas (`\rules`, `\whitespace`) are interpreted differently from regular wikitext body elements.

**PROBLEM:**
If you place HTML elements (like a `<style>` block) or normal wikitext *before* or *in between* `\define` statements, the TiddlyWiki parser switches from "pragma mode" to "body mode". Any subsequent `\define` macros will not be parsed as macros, but instead will be rendered directly to the screen as raw text.

**STANDARD OPERATING PROCEDURE:**
All `\define` macros and pragmas MUST be placed at the absolute top of the `.tid` file, consecutively, before any HTML tags, styles, or standard wikitext. If you need to add a `<style>` block or HTML, place it *after* all `\define` blocks have concluded.

# Headless Testing of TiddlyWiki Logic (The Chrome Harness)

**CONTEXT:**
TiddlyWiki filter syntax and widget/action behavior are subtle and under-documented. The built monoliths (`variants/pre.html`, `src/lithic.html`) embed the entire wiki as a JSON tiddler store, and Chrome can boot them headlessly. Empirically validating filter chains and action wikitext this way caught multiple real bugs that reading minified core source alone did not (sortsub operand parsing, `$let` first-element resolution, `$action-setfield` list mangling).

**STANDARD OPERATING PROCEDURE:**
1. **Tools:** Node.js is NOT reliably available. Use Python 3 + headless Chrome for execution — the concrete paths for THIS machine live in the gitignored `.freebuff/local/agents.local.md` (relative to the repo root), so root `agents.md` stays environment-agnostic.
2. **Pick a bootable build:** use `src/lithic.html` ONLY — `variants/pre.html` is a STALE build and must NOT be used for validation (it has misled us before). `assets/blank_no_server.html` is NOT bootable (bare store, no boot machinery).
3. **Boot readiness quirk:** the Lithic build ships a custom `wiki.js` whose `getTiddlers()` takes an OPTIONS object and EXCLUDES system tiddlers by default (returns ~0 on a plugin-heavy monolith) — so `getTiddlers().length > 0` is NOT a valid readiness probe. Probe `$tw.wiki.getTiddler('$:/plugins/sq/streams')` instead (plus `$tw.rootWidget` for widget work).
4. **Inject a harness:** write a small Python builder that reads the build HTML, inserts a `<script>` test block immediately before `</body>`, and writes a copy (e.g. `scripts/_test.html`). The harness polls `window.$tw && $tw.wiki && $tw.rootWidget` on a `setInterval` (boot is asynchronous), then runs assertions into a `<pre id="out">` element.
4. **Run it:** `"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --disable-gpu --no-sandbox --virtual-time-budget=30000 --dump-dom "file:///.../_test.html"` then extract the `<pre id="out">` text (sed between the `<pre>` tags and strip tags).
5. **Invoke context-menu action wikitext:** `wiki.parseText("text/vnd.tiddlywiki", body).tree` → `$tw.rootWidget.makeChildWidget({type:"widget", children: tree})` → `w.render(container, null)` → recursively walk the tree calling `invokeAction(node, null)` on every widget that exposes it.
6. **Invoke a single action widget directly:** build `{type: "action-listops", attributes: {name: {type:"string", value: ...}}}`. CRITICAL: call `widget.render(host, null)` BEFORE `invokeAction()` — attributes (e.g. `$subfilter`) are only computed in `render()` → `computeAttributes()`/`execute()`. Skipping render silently no-ops the action.

**GOTCHA:** fixtures must be realistic. Alpha-sort tests passed with space-less titles but failed on real data: use bracket-wrapped, space-containing list entries (e.g. `[[6th August 2026@1:40:02.470]]`) and multi-child streams.

**HARNESS PHILOSOPHY — it's a sieve, not an oracle:** the harness reliably filters out parse-level bugs (filter errors, wrong operator semantics, list mangling). Do NOT chase harness perfection — results that depend on widget-scoped variables (which don't resolve headlessly in this build) go straight into the user's meatspace checklist with specific instructions, and unexpected edge cases are passed down for meatspace verification rather than debugged in the harness. Also: the extraction regex MUST allow attributes on the pre tag — the injected `finish()` sets `style`, so match `<pre id="out"[^>]*>(.*?)</pre>` (a bare `<pre id="out">` silently fails and falls back to a truncated tail dump).

**KNOWN HEADLESS LIMITATION (this build):** widget-scoped variables do NOT resolve in headless boots. `$tw.rootWidget.setVariable("x","3")` followed by `filterTiddlers("[<x>]", r)` yields `[""]`, and `<$let>/<$set>`-scoped variables render blank through `$list`. Only VARIABLE-FREE filter chains are reliably verifiable headlessly — substitute literal titles instead (e.g. `[[Title]get[field]]`). Any behavior that depends on widget-scoped variables (like the context-menu label keys) must be verified by the user in meatspace.

# TiddlyWiki Filter & Widget Gotchas (Field-Tested)

**CONTEXT:** all verified empirically against TiddlyWiki 5.4.1 headlessly; several contradict the official docs or common usage.

1. **`sortsub` is broken for field operands.** `sortsub[{!!text}trim[]lowercase[]]` (the documented idiom) evaluates to nothing in 5.4.1 — the operand is parsed as a literal title. Use the `sort` operator directly: `[enlist{!!stream-list}sort[text]]` sorts the input by a field, case-insensitively by default.
2. **`enlist[]` reads its OPERAND, not the input.** To parse the filter's input as a list use `enlist-input[]` — that is why streams writes `enlist{!!stream-list}` (operand form) everywhere, and why conditions must use `[<currentTiddler>get[stream-list]enlist-input[]count[]!match[0]]`.
3. **NEVER write a list field via `$action-setfield` from a filter result.** `$value={{{[enlist<var>]}}}` writes bare titles; TW's list parser treats spaces as separators, so `6th August 2026@1:40:02.470` shreds to `2026@1:40:02.470`. Always use `$action-listops` with `$subfilter` (or `$filter`) — core parses the field via `getTiddlerList` and writes it back via `stringifyList` as `[[bracketed]]` entries that round-trip.
4. **`$action-listops` `$subfilter` semantics:** core prepends `"[all[]] "` to the subfilter, and `[all[]]` with an EMPTY operand is an IDENTITY (returns the input unchanged) — so the subfilter genuinely operates on the parsed list (e.g. `$subfilter="[sort[text]]"` sorts the list in place; `reverse[]` flips it).
15. **A `-` filter run whose content is a bare prefix/field operator is evaluated as a SOURCE, not against the accumulated list** — it therefore sees real tiddlers only and silently leaves every shadow in place (see the `.lith` Exporter Rules section for the measurement). Write the source explicitly: `-[all[tiddlers+shadows]prefix[x]]`. Two related traps: `:except[a b]` pipelines its clauses as AND (one `:except` per clause, or none of them apply), and a prefix run given a literal operand cannot contain brackets.
5. **Multi-value `$let` variables expose only their FIRST element as the string `value`** (the full array lives in a hidden `resultList`). So `[<children>match<ascending>]` silently compares first elements only — effectively always "equal" for permutations sharing the first item. Compare JOINED strings instead: `$let sorted={{{[enlist{!!stream-list}sort[text]join[|]]}}}` then `[enlist{!!stream-list}join[|]match<sorted>]`.
6. **Use `join[|]` as a list-join delimiter, not `join[,]`** — commas are legal in tiddler titles; `|` is not, and `join[|]` parses fine as an operand (verified).
7. **`has[done]` checks a FIELD; `tag[done]` checks the TAG.** The streams interactive checkbox stores state as the `done` tag — a `has[done]` condition silently never matches.
8. **Avoid literal bracket-prefix operands** like `prefix[[x] ]]` — in the current build they produce a hard `Filter error: Missing [ in filter expression` (verified: `[addprefix[[x] ]]]` and every strip/prefix chain using `[[ ] ]]`-style literals fails). Define prefixes as variables (`$vars todo1="[ ] " done1="[x] " num1="<<num>> "`) and use `prefix<todo1>` / `removeprefix<todo1>` — the established streams pattern. CRITICAL: after a `~` separator, a variable run MUST be bracketed — `~<done1>` is parsed as the LITERAL TITLE `<done1>` (returns `["<done1>"]`), while `~[<done1>]` resolves the variable (returns `[""]` when unset). Verified both forms.
9. **Don't chain `+[op...]` after `~` union alternatives** — attach the chain inside each run: `[<t>removeprefix<done1>addprefix<num1>] ~[<t>removeprefix<done2>addprefix<num1>]`.
10. **`match` compares single strings.** For list-equality, join both sides first (see #5).
11. `removeprefix` / `addprefix` / `prefix` / `then` / `else` / `count` / `reverse` / `first[]` / `is[tiddler]` / `tag[]` are all verified working as expected.
12. **`$action-listops` `$tags` expects FILTER entries with bracket-wrapped tags.** `$tags="-[done]"` parses as an invalid filter and SILENTLY writes the error string `Filter error: Missing [ in filter expression` into the tiddler's `tags` field (corrupting it). Use `$tags="-[[done]]"` / `$tags="+[[tag]]"` (the `+`/`-` prefix with `[[brackets]]`). Verified: `-[[done]]` cleanly removes the tag; this bug shipped once in cycle-leadmark and was caught by the harness.
14. **Expressing bracket characters in filter strings: use regexp unicode escapes, not literals.** Literal `[ ] ` operands get mangled (see #8), but a regexp operand can carry the characters as escapes and parses cleanly: `[all[]search:text:regexp[\x5B \x5D]]` (character class matching `[`, space, `]`) — verified headlessly; it even catches plugin bundles whose JSON `text` contains brackets. CAVEAT for harness probes: the JS string layer decodes `\x5B` → `[` before TiddlyWiki sees it, so in JS test strings write `\\x5B` (double-backslash) so the filter receives a literal `\x5B`; in wikitext the raw `\x5B` reaches the filter parser intact and only the regexp engine decodes it.
13. **`~` between runs is IF/ELSE, not union.** `[[A]] ~[[B]]` yields `["A"]` — the second run is ONLY evaluated when the accumulated results so far are empty (`[<v>match[zzz]] ~[[LIT]]` → `["LIT"]`). Great for fallback/else chains (e.g. the ctx-label keys), but you cannot accumulate values across `~` runs. Verified on the current build (core 5.4.1); a code review once flagged two false-positive bugs by assuming union semantics.

# Streams Context Menu Extension & Streams Internals

**CONTEXT:** the vanilla Streams plugin source is NOT in the repo (fetched at build time via `external.yml`); a reference copy lives at `assets/streams_and_fusion.json` (a JSON array of plugin blobs — each blob's `text` field is itself JSON containing that plugin's tiddlers). Streams-specific patches live in `wiki/local-plugins/lithic-patch-streams/`.

**Adding an item to the nodestream right-click menu** (the Streams context menu — distinct from the standalone generic context-menu plugin):
1. Create a tiddler tagged `$:/tags/streams/contextmenu` with:
   - `sq-contextmenu-name: <menu label>` (shown in the menu)
   - `text:` = the action wikitext (invoked on click; `currentTiddler` is the right-clicked node)
   - OPTIONAL `sq-contextmenu-condition:` = a filter; if it evaluates empty the item is hidden (e.g. `[<currentTiddler>get[stream-list]enlist-input[]count[]!match[0]]` hides on childless nodes). The template override in lithic-patch-streams (`$:/plugins/sq/streams/contextmenu/contextmenu-template`) wraps every item in a conditional `<$list>` with an `else[yes]` fallback, so items without the field remain visible — backward compatible.
2. Operate on children with `[enlist{!!stream-list}is[tiddler]]`; operate on the node itself when childless by branching on `[enlist{!!stream-list}is[tiddler]count[]!match[0]]` with an `emptyMessage` that re-runs the ops on `<<currentTiddler>>`.
3. For multi-target ops use `<$list filter="..." variable="target">` with inner `$let`/`$list` conditionals and `$action-setfield`/`$action-listops`. Widget attributes are computed at RENDER time from pre-click state, so keep per-target transitions free of cross-target dependencies.
3b. **NEVER iterate a multi-value `$let`/`$vars` variable through `$list filter="[<var>...]"`** — a multi-value variable exposes only its FIRST element to filters (the full array lives in a hidden `resultList`; see gotcha #5). Real shipping bug: a sibling list computed as `targetList={{{ [<currentTiddler>get[parent]get[stream-list]enlist-input[]is[tiddler]] ~[<currentTiddler>] }}}` and iterated with `[<targetList>is[tiddler]]` silently processed only the FIRST sibling — meatspace found it ("only top item cycled"). Re-read the field instead: `$set name="currentTiddler" filter="[<currentTiddler>get[parent]]" select="0"` then `[enlist{!!stream-list}is[tiddler]]` (the established pattern alpha-sort and the children branch use). Root fallback: gate on `[<currentTiddler>get[parent]get[stream-list]enlist-input[]is[tiddler]count[]match[0]]` and iterate `[<currentTiddler>]`.
4. Reference implementations: `$__lithic_streams_contextmenu_alpha-sort.tid` and `$__lithic_streams_contextmenu_cycle-leadmark.tid`.
5. **Dynamic labels (children vs siblings):** the template computes a label key from the target node (`currentTiddler` in the template is the right-clicked node; `contextmenu-state` is in scope). A `~` else-run chain picks `sq-contextmenu-name-children` (has children), `sq-contextmenu-name-siblings` (childless with peers), or the base `sq-contextmenu-name` (childless lone node); the title is `[<listItem>get<ctxLabelKey>] ~[<listItem>get[sq-contextmenu-name]] +[first[]]`. Items opt in by defining the extra fields; non-dynamic items fall through to `sq-contextmenu-name`.
6. **Hover-gated preview highlight (no JS):** the streams context menu is transcluded ONCE per stream at the top level of `.stream-root` (in `nodes-list-template`) and TW's popup `$reveal` renders inline, so `.stream-root:has(.sq-contextmenu .sq-ctx-item:hover) [data-node-title="X"] { ... }` scopes the hover state cleanly. A wikitext stylesheet (tagged `$:/tags/Stylesheet`, resolving the state via `[prefix[$:/state/sq-context-popup]get[current]!is[blank]first[]]`) emits per-title selectors for the affected rows (children rows, or the parent's `stream-list` when childless) gated by that `:has()` — for both a palette-aware bullet (`<<colour primary>>`) and the node background (the contrast core's `--lithic-c-notify-bg`/`-fg` roles -- the palette's own notification/message pair with a contrast-locked ink. Those roles are derived from the exact fields this band used to hard-bind, so both bands stay identical while the ink is repaired on palettes whose raw pair is unreadable, e.g. Nord). Requires `:has()` (Chrome/Edge 105+, Firefox 121+, Safari 15.4+). Reference: `$__lithic_streams_styles_ctx-preview.tid`.

# Theme-Responsive Styling (The `<<colour>>` Macro)

**CONTEXT:**
Lithic users frequently switch between light and dark themes (palettes). Hardcoding HEX or RGB colors in styles will break the UI contrast when the theme changes.

**STANDARD OPERATING PROCEDURE:**
When applying custom styling, always use TiddlyWiki's core `<<colour>>` macro to resolve colors dynamically from the active palette, rather than hardcoding static hex colors.

**Common Lithic Palette Variables:**
- `<<colour primary>>`: The main accent color (great for borders, highlights, active states).
- `<<colour background>>` / `<<colour foreground>>`: The base wiki background and text color.
- `<<colour tiddler-background>>`: The background color of standard tiddler frames.
- `<<colour code-background>>`: Very subtle off-background color (great for subtle UI highlights).
- `<<colour muted-foreground>>`: Dimmer text for secondary or inactive information.
- `<<colour selection-background>>`: The highlight color used when selecting text.

**Example Implementation:**
If injecting styles via a `<style>` block in wikitext, you can evaluate the macro directly:
```css
<style>
.my-custom-class {
    background-color: <<colour code-background>>;
    border-left: 2px solid <<colour primary>>;
    color: <<colour muted-foreground>>;
}
</style>
```

# Environment & Workflow Notes

- **Environment-agnostic policy:** root `agents.md` deliberately carries no machine-specific paths. Concrete tool paths (Python, Chrome), the notification-chime convention, and machine-specific workflow details live in the GITIGNORED `.freebuff/local/agents.local.md` (relative to the repo root) — read it if present.
- **`src/lithic.html` is still not byte-reproducible across machines, for a reason no lockfile can fix (measured 2026-09-21):** building the wiki locally and diffing against CI's committed artifact gives the same 48 tiddlers in the same order, with 19 plugin bundles differing **only in JSON key order** — every tiddler inside them hashes identically. The inner order follows the order tiddlers were loaded from the plugin folders on disk, which differs between Windows and the Ubuntu runner (the ext4/htree order is stable for a given runner, so CI-vs-CI agrees while local-vs-CI does not). Practical consequences: a locally rebuilt `lithic.html` will not match the committed one, so do not treat that artifact's diff as meaningful, and never "fix" a divergence by copying a local build over it. Closing it properly means sorting titles at whatever point folds plugin tiddlers into the bundle JSON (not yet located) rather than relying on enumeration order.
- **Builds:** `src/lithic.html` is the current monolith (Tauri rolls it up) — use it for headless validation. `variants/pre.html` is a STALE build — do NOT use it. `assets/blank_no_server.html` is NOT bootable.
- **Line endings:** repo `.tid` files (and `agents.md`) are CRLF. Editing tools write LF — convert to CRLF BEFORE running `trim.ps1`, and pass ONE file path per `trim.ps1 -Files` invocation.
- **Reading core sources:** every built HTML embeds all plugins as a JSON array inside `<script class="tiddlywiki-tiddler-store" type="application/json">`. Locate the `$:/core` plugin object (the preceding character must be `{`), then `json.loads(core["text"])["tiddlers"]` yields every core module (widgets, filter operators) — far more reliable than grepping minified blobs. A module lives at a key like `$:/core/modules/widgets/action-listops.js`.
- **Rollup JSON for meatspace testing:** after each major iteration that changes plugin tiddlers, generate a standalone importable rollup so the user can verify in their live wiki: `python scripts/make-rollup.py rollups/<date>-<feature>.json <changed .tid files...>`. It emits the TiddlyWiki import format (a JSON array of tiddlers with every frontmatter field + `text`, including shadow-override titles like `$:/plugins/sq/streams/contextmenu/contextmenu-template`). Sync the rollup to the primary checkout; the user imports it into their live wiki and hand-tests.
  - **Always use this script - never hand-roll the JSON.** The format is a flat top-level JSON array of flat tiddler field objects; any wrapper (`{"tiddlers": ...}`, `{"tiddler": {...}, "body": ...}`) makes the importer show an empty/blank tiddler list. This bit us twice. For ad-hoc tiddlers (e.g. a self-test page), write them as a real `.tid` file first (scratch/ is fine) and pass them to the script like any other.
  - **Before handing the rollup over, prove it imports:** run the array through the real deserializer (`require('tiddlywiki/core/modules/deserializers.js')['application/json']` - see `scratch/rollup-check.js`) and confirm every tiddler has a title and non-empty text.
  - **Format alone is not enough - also parse- and render-gate changed widget/macros:** importing cleanly says nothing about whether the wikitext still parses. Real shipping bug: replacing `fullChart={{{ [...] }}}>` (filter transclusion + widget-tag close) with `fullChart=<<pyramidData>>` silently swallowed the tag's own `>` (the macro's `>>` ate it), the `<$let>` never closed, and the whole sidebar rendered as literal `</$let>` text. Never end a widget tag on a bare `=<<macro>>` attribute - wrap in `{{{ [...] }}}>` or add the explicit `>`. Gate changed tiddlers by rendering them in the real built wiki (parseTiddler + makeWidget from `$tw.rootWidget`, container attached to `document.body`, poll for async mermaid SVG) and asserting no literal widget syntax (`</$let>`, `<$mermaid`, `classDef`) leaks into text nodes - see `scratch/render-gate.js` (also seeds a stream + `$:/StoryList` because the pyramid renders empty without one).
- **Critical (field-tested 2026-09-16): in mermaid 11 html-label mode the label DOM is `foreignObject > div.labelBkg > p > span.edgeLabel`, and mermaid's own internal stylesheet paints the light `edgeLabelBackground` (`rgba(232,232,232,0.8)`) on the `<p>`/`.labelBkg` - theming only the span/div leaves a white-on-white box that computed-style checks on spans happily report as "themed". Any edge-label theming rule set MUST include `foreignObject p` and `.labelBkg`, and gates must assert **no opaque light background painters anywhere inside `foreignObject`** (scan every element; skip bare-SVG elements for background-color since it computes but never paints there) - see the light-painters check in `scratch/edge-contrast-gate.js`.

# How This Repo Is Verified

The commands, in one place. They were restated (with their assertion counts) at the end of every round's entry until 2026-10-02, which said the same thing sixty times and made the log three quarters of this file. **A round now says which of these it ran, not how many assertions they hold**, and it does not claim one it could not run: a check the machine cannot perform is worth saying out loud ("the desktop crate is CI-verified only on this box, because it needs GLib and WebKitGTK"), and is never worth silently skipping.

- **Everything at once:** `npm run check:push`. It is the push gate, and it chains the copy rule, the locale pin, the artifact freshness check, the offline launcher gate and `scripts/pre-push-check.mjs` (which itself runs the phone's compile face, the lockfile sync, the workflow YAML sanity, the shim build tag, the release trigger, and `cargo check`, `clippy` and `test` for both crates). A failure here is the answer to "is this pushable".
- **The launcher's own gates:** `npm run check:copy` (no em dashes or en dashes in any launcher or shim file), `npm run check:locale` (the language pin rewrites the redirector and the install manifest and nothing else), and `npm run check:offline` (the launcher's offline mode, in a browser). One more, `node scripts/check-launcher-artifact.mjs`, compares the committed `src/launcher.html` against a fresh build of `launcher-ui/`, which the server image and the PWA manifest both ship by name: run it after any launcher-source change, because the first run after an edit reports STALE and writes the fresh build into the tree, and the second reads that copy back as OK. What it writes is scratch like any other local build, and the KNOWN GAP above is the one place this gate and the CI-only policy disagree.
- **The launcher's tests:** `npm --prefix launcher-ui run check` (svelte-check; must be 0 errors and 0 warnings) and `npm --prefix launcher-ui run test` (the unit suite, which is `node --experimental-strip-types --experimental-specifier-resolution=node --test src/*.test.ts`). `npm test` is the same suite through a clean `npm ci`.
- **The Rust:** `cargo test --manifest-path shim/Cargo.toml` and `cargo clippy --manifest-path shim/Cargo.toml --all-targets -- -D warnings`. The desktop crate is the same three commands against `src-tauri`, and it needs GLib, GDK and WebKitGTK development packages: run them where those exist (CI does) and say so when they do not exist here.
- **The phone's compile face (one command, no SDK, no NDK):** `npm run check:android-face` — `scripts/check-android-face.mjs`, which is also a step in the Rust Check workflow and in `scripts/pre-push-check.mjs`. Android is the only platform where `lib.rs` resolves `gitcore` to `gitcore_unsupported` rather than the libgit2 module, so it is the only arrangement in which the sync contract's surface is checked against the stub, and no flag switches a host build into it. The script copies `src-tauri`, `shared/` and `src/` into a throwaway directory, rewrites the 23 `cfg(target_os = "android")` predicates in that copy to `all()`, and checks the library there against the crate's own target directory, so only the crate itself is compiled. Three things it arranges are asserted in the copy rather than trusted (the libgit2 module pruned, the stub as the git face, the git half of `shared/sync_core.rs` pruned the way the phone prunes it), because a rewrite that stopped matching the crate's spelling would compile the desktop's arrangement and pass. Two limits are deliberate and stated at the script: the phone's document answers in `platform/android.rs` call Tauri APIs that exist only in a Tauri-for-Android build, so those bodies keep the phone's pruning and the APK job stays their gate; and the verdict line carries cargo's own evidence, with a pass refused outright when nothing was compiled — the first version of this gate read `src_path` off `message.target` when cargo puts it beside `message` on the JSON line, dropped every message as a stranger's, and reported a clean pass over a copy that failed with five `E0425`s.
- **The browsers:** `npm run test:puppeteer` (the launcher smoke suite, which drives the real built artifact in a real browser; `PUPPETEER_EXECUTABLE_PATH` points it at a system Chromium when it cannot download its own) and `npm run gallery` (the UI gallery, which photographs every state the launcher can be in). The smoke suite is the one that catches what the unit suites cannot: layout, keyframes, and whether a control is reachable at all. `npm run check:pdf-plugin -- <artifact>` and `npm run test:pdf-artifact <artifact> [--pdf file]` are the PDF import pair and they answer different questions: the first reads the artifact and fails when the import plugin's JavaScript is not byte-for-byte what its source says (the prod uglify pass re-minified it once and every imported PDF page came out white, so this is the gate), the second boots the artifact in headless Chrome, drops `scripts/fixtures/pdf-import-smoke.pdf` on it, and measures the ink on every page the import renders. The first is wired into the prod build's verify step; the second needs an artifact and so is a local tool, and `--pdf` runs the same drive against your own document.
- **The Linux artifact:** `bash scripts/build-shim-appimage.sh --name NAME --output-dir DIR [--work DIR]`. `--work` keeps the downloaded `appimagetool` between builds instead of fetching it again. Worth doing after any change to the launcher's HTML, the shim, or the engine payload, because it is the shape a user actually runs.

# A Browser Extension Prong Is Closed (INTENTIONAL, DO NOT BUILD)

**DECISION (2026-10-27):** Lithic ships no browser extensions, for Firefox, Chrome, Edge or Firefox for Android, and no WXT packaging pipeline. The motive that started the idea (a just-works, account-synced prong whose data lives in the browser's own profile sync) does not survive the platform, and what is left is a third distribution shape with no capability of its own. Treat it as closed unless the developer reopens it, and read the reasons before proposing it again.

**WHY:**
1. **The sync half is not obtainable.** `storage.sync` is item-capped (around 8 KB per item and 100 KB per account) and does not replicate IndexedDB, and `unlimitedStorage` does not lift it. A Lith is megabytes, so profile sync can never be its source of truth or its backup. The premise the prong was founded on is gone.
2. **The engine cannot run in an extension page.** MV3 forbids inline script and `unsafe-eval`, and TiddlyWiki boots by evaluating its module tiddlers, so the engine needs a sandbox frame. A sandbox frame has an opaque origin with no IndexedDB and no localStorage, so storage would have to cross a postMessage bridge pinned to the saver's `get`/`set`/`del` contract.
3. **The mount path assumes the launcher owns the document.** The launcher `document.write`s the engine over itself. In an extension the privileged page has to stay alive behind that frame, so saves, downloads, dirty state and the payloads parked on `window` (PDF, whiteboard) all need a channel they do not have. That is a re-architecture of the boot plus a second engine host kept in step forever, with every launcher change then tested in two shapes.
4. **No extension filesystem API exists, and the one that did is dead.** `chrome.fileSystem` was a Chrome Apps API, deprecated in 2020 ([reference](https://developer.chrome.com/docs/apps/reference/fileSystem)), and Firefox 57 removed XPCOM and `nsIFile` with no WebExtensions replacement. Native messaging is the only route with real file access, and it is a bridge to a separately installed helper program: that program is the desktop app, which this repo already ships.
5. **Firefox will never have the File System Access API.** Mozilla's standards position is [negative (#154)](https://github.com/mozilla/standards-positions/issues/154), the picker-only proposal is [defer (#738)](https://github.com/mozilla/standards-positions/issues/738), and [Bugzilla 1246236](https://bugzilla.mozilla.org/show_bug.cgi?id=1246236) is still NEW after ten years. So on the one platform with a motive, an extension could never write a real file in place, and OPFS is another origin bucket that a site-data clear takes with it.
6. **The platform with the only motive is where extensions are weakest.** On Firefox for Android there is no native messaging, no downloads API ([Bugzilla 1538348](https://bugzilla.mozilla.org/show_bug.cgi?id=1538348)) and no pickers, so an extension would hold a Lith's only copy in extension storage with no extension-level way out; installation there goes through addons.mozilla.org rather than a sideload, so the platform that justifies the build is also the one carrying a distribution gate.
7. **On Chrome and Edge it is redundant rather than a bonus.** Extension pages there can reach the pickers, since those are a web API, so it would not downgrade those users as first assumed. But in `webapp` mode Chrome already writes real files in place through the PWA, so a Chrome or Edge extension buys nothing that does not already exist, at the price of two store listings.
8. **It muddies the product for the person using it.** A third prong with no distinct capability turns "which one do I use" into a real question at first contact, while the difference between site storage and extension storage is an explanation only: to the person, both are just "in the browser". The one genuine niche (Firefox Android storage surviving a site-data clear) is narrow, unmeasurable because nothing here reports, and already mitigated by add-to-home-screen, `navigator.storage.persist()` (which guards eviction, never a manual clear) and downloading a copy.

**WHAT WOULD REOPEN IT:** a capability that only an extension origin provides and the PWA cannot, such as an integration against a running instance. That would justify the packaging on its own merits, with Android as a rider rather than the whole reason. Nothing in the feature set today qualifies.

**ALSO SETTLED HERE:** the install offer stays absent on Firefox Android, because Firefox does not install PWAs from a manifest ([MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)), so `pwa-install.ts` grows no Firefox path. The Firefox desktop pass this discussion produced is `npm run test:firefox` (20 checks, wired into `launcher-firefox.yml`); Firefox desktop and Safari are the two desktop browsers that land in the `index-db` fallback in `webapp` mode, and that path is measured intact.
