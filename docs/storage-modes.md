# Storage Modes: What Owns Your Data

Lithic always saves somewhere. The mode decides how much a mistake, a dead disk or a cleared cache can cost you. Every mode layers the same tiers: version history, a working copy, and, where the platform allows it, a remote mirror. Each tier survives a different failure: a mistake, a dead disk, a destroyed server. When tiers disagree about a file, the more durable one wins.

The launcher detects the mode from the platform it runs on. There is no setting to choose and no account to create. The last column is the only copy that is genuinely yours.

| How you run Lithic | Just works (no setup) | Implicit (happens without being asked) | Source of truth |
| --- | --- | --- | --- |
| **PWA: Chrome/Edge, desktop** | Open a `.lith`, edit, save. A recent entry returns to the same file, so saves keep landing in it | Saves go back to the file you already picked instead of asking again. Version history and the search cache stay on this device | **The `.lith` file you picked** |
| **PWA: Safari on macOS/iOS** (Firefox and Android Chrome behave the same way) | Open, edit, save. The browser's storage *is* the document. No file is opened or written, because these engines have no File System Access API. Opening a local `.lith` reads a copy in, and the original is never written back | New wikis and saves become IndexedDB entries, marked with an amber warning mark whose tooltip explains the volatility. Clicking it opens version history, the only route to a hard copy (it downloads `<name>_recover_<stamp>.lith`). Recents **Rebuild** is hidden, since nothing on disk can be re-listed. The footer control is **Backup & Reset Recents** instead | **This browser's storage on this device.** It is volatile: cache eviction, "clear site data" or an uninstall takes it |
| **Desktop app (Tauri)** | Open, edit, save to real files. Recents rebuild by reindexing the folders you point it at | Rust writes the save straight to the path you already own. History and caches stay device-local. Nothing talks to a server | **The `.lith` file on your disk** |
| **Desktop app + GitHub backup** | Real files plus an off-device copy. Connect a folder to a repository once, and every save is committed and pushed to `main` | Your folder always wins. GitHub is read only for files the folder lacks. A document that differs on both sides keeps its local copy. Nothing on your side is overwritten, and deletions never propagate. The icon turns green only after GitHub confirms it accepts a push | **Your folder.** GitHub is a restore-only mirror, and every remote copy it replaces survives in commit history |
| **Self-host (Docker / LXC / Railway)** | Any browser reaches your wikis by URL. Nothing is installed on the client | Saves arrive as diffs the server applies and commits into `/data`. WebDAV, the sync watcher, `cp -r /data` backups and the rollback UI all read that one tree | **The server's `/data`.** Your server and your disk, but not your laptop |
| **Self-host + GitHub backup** | The server folder plus an off-server copy in a repository you own | `/data` becomes a git repository. Wikis only the remote has are brought down on connect, then the server's state is published. Saves and watcher passes commit and push, and a failed push restarts the backup | **The server's `/data`**, with git holding history and rollback. If the remote has diverged, its files are applied over the server's tree and the server's version is kept in history |

## Notes

* **Version history is device-local in every mode.** It is not a server or GitHub feature. The clock icon lists `full`, `step` and `sync` entries for wikis opened on this device, and the oldest are pruned first when storage runs low. See [Version History](version-history.md).
* **The Mac/iOS fallback is detected, not chosen.** A browser without the File System Access API lands in browser-storage mode on its own. Append `?storage=file` or `?storage=index-db` to the launcher URL to force either one while testing.
* **The launcher asks the browser not to evict its storage.** `navigator.storage.persist()` is requested when a Lith is written, once per session, and the answer is used silently. Chromium decides from its own heuristics, Firefox asks the person, and Safari keeps its own deletion policy. See [iPhone and iPad](iphone-ipad.md).
* **The browser-storage fallback can hand you everything it holds, and asks before it forgets.** In browser-storage mode the footer control is **Backup & Reset Recents**. It lists a row per recent wiki with a download control and a mark beside each, plus **Download Full Backup** for the whole store at once. **Reset Recents** stays disabled until every row has been downloaded or the full backup has been taken. A browser that cannot confirm a download counts as done, because Safari and Firefox have no file picker to confirm with. The file is one JSON document, `lithic-instance-backup-<stamp>.json`. It holds the recent list, each wiki's current text, its version history, any unsaved edit, and the saved instances with their cached icons. The `<stamp>` is the moment the file was taken, to the second.
* **Dropping that file back merges it, unless a name is in the way.** A dropped `.json` is read as an instance backup first, and falls through to the ordinary tiddler-payload import when it is not one. A name this device already holds refuses the whole file and lists the clashing names. The comparison ignores case. Rename or remove those, then drop the file again. Saved instances arrive additively: an address this device already holds keeps its entry and icon, and the rest are appended. Restoring someone else's backup can add instances but never removes one.
* **The self-host launcher lists the server's store and nothing else.** Its file action is **Upload a Lith**. The `.lith` you pick is sent to the store and opened from there. A name already on the server is replaced only after you confirm, because this mode keeps no local copy to fall back on. Each row shows the size the server reports rather than the date it was written. Each row also carries a × that deletes the file from the server, and it asks first. **Rebuild Recents** reads the store again and indexes each Lith in it. Search reads that index, so a word that appears only inside a Lith still finds it. **Reset** is not offered, because the list is not this device's to clear. When the instance cannot be reached, the panel lists this device's saved copies instead, and the footer control becomes **Backup Recents**.
* **An instance's icon belongs to the instance.** The mark beside a self-hosted launcher's title is the instance's own `/mstile-150x150.png`, read from the address that served the page. An instance that has never published a set, and a page with no instance behind it, fall back to the shipped mark. A chosen emoji for the heading is stored in the instance's store, so anyone opening it in any browser gets the same favicon and mark. An instance that cannot be asked still shows the icon this browser last saw.
* **Instance Management is one dialog in every mode.** Clicking the mark opens it. It holds the icon picker where there is an instance to set one, a **View Docs on GitHub** link, and **Download Full Backup**. The desktop app draws no footer GitHub link, so the dialog's link is its only way to the repository there.
* **A self-hosted launcher can turn the server's backup on.** The cloud button in the heading opens the desktop app's GitHub dialog, pointed at the instance. The repository belongs to the server: its `/data` is the git tree, and its saves and watcher passes do the committing and pushing. Disconnecting deletes the server's token, which stops its watcher pushing. The remote and the wikis stay where they are.
* **Removing a bookmark also drops the app's cached copy of that instance.** An instance's page, scripts and icons live under its own origin, so a redeployed instance could otherwise keep serving an old launcher. Removing a bookmark now clears that origin's cached copy too. Cached wikis and a saved login are not touched. This applies to the desktop app on Windows for now. In a browser or PWA the bookmark removal is all it does.
* **Update Install closes the windows in its way, then closes itself.** An update overwrites the installed copy, which the operating system refuses while a program runs from it. The launcher asks other Lithic windows on this machine to close first. Once the new copy is on disk, the window you pressed the button in closes too. A window with a Lith open is never closed. The update is refused and names the Lith instead. This applies to the desktop app on Windows and the WebKitGTK AppImage. A Mac bundle installs by drag and never offers an update. The Linux shim serves a browser, so its launcher line says where the file went.
* **Search reaches bookmarked instances on the desktop app.** The app reads cached wikis from the profile it keeps for each origin it has visited. Each instance gives one hit, which orients you. The panel beside it opens that instance already searching for the same words. No request leaves the machine, and no instance is loaded to answer. This applies on Windows for now.
