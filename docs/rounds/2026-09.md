What a round's entry is for: the decision that was actually made when it was not obvious, and the
trap that would otherwise be walked into twice. Not a walkthrough of the diff (the code says what
the code does, and this repo writes its rationale at the code), and not a list of test counts:
the commands that verify a change are stated once, in the "How This Repo Is Verified" section of
`agents.md`, and a round says which of them were run rather than how many assertions they hold.

A round's verification tail is therefore dropped when it is only counts. A caveat is not:
"Left open", "Unverified" and their like are kept, because a known hole is the most useful thing
in here.

- **Launcher UI builds are pinned by `launcher-ui/package-lock.json` (2026-09-21):** the artifact-emitting toolchain (vite, svelte, rollup, esbuild) is installed with `npm ci`, not resolved fresh from the registry. The old `npm --prefix launcher-ui install --no-package-lock` resolved caret ranges on every machine, so a CI release and a local build compiled the same sources with different tool patches and emitted different bytes — and because `check:push` compares the committed `src/launcher.html` against a local rebuild, every race between a push and CI's own commit ended in a merge conflict over a file nobody had edited. Measured drift at the time of the fix: rollup 4.63.1 vs 4.63.4, svelte 5.56.10 vs 5.57.1. Never reintroduce `--no-package-lock`, and commit the regenerated lockfile in the same commit as any dependency change. The root toolchain is pinned the same way by the root `package-lock.json` (that is what emits `src/lithic.html`), and the Rust side by `src-tauri/Cargo.lock`; all workflows install with `npm ci` and cache `~/.npm` keyed on the lockfiles.

- **Mermaid 11 label whitespace & font peculiarities (field-tested 2026-09):** the mermaid wrapper (`wiki/local-plugins/lithic-patch-mermaid/`) `decodeHtmlEntities`es the diagram body, and Mermaid 11's flowchart pipeline runs every quoted label through `trim()` plus whitespace collapsing (markdown-text path splits on `[ \t]+` and rejoins). **ALL label whitespace is therefore collapsed AND trimmed - U+00A0 (`&nbsp;`) included.** Any macro trick padding labels with nbsp entities or trailing spaces to stop text clipping is silently deleted; do not re-add padding hacks. The REAL cause of clipped label edges is a **measure/paint font mismatch**: mermaid measures label widths with its `fontFamily` config (default `sans-serif`), but the SVG paints with whatever CSS resolves (in the sidebar that has been the serif body font) - a wider paint font overflows the measured box. Fix = make both sides agree: pass `fontFamily` on the `<$mermaid>` widget (the Pyramid sidebar pins `Vollkorn`, embedded locally in `$:/lithic/fonts/vollkorn`), and never measure before the webfont is available - the wrapper defers `mermaidAPI.render` until `document.fonts.ready` (3s timeout fallback) for exactly this. Note the wrapper treats a **font-only** per-widget init (sole injected key `fontFamily`) as NOT self-styling, so the palette-default CSS still applies; any other injected key, or `%%{init}`/`style`/`classDef`/`linkStyle` in the body, flags the container `mm-user` and opts the diagram out of the palette defaults. Two more field-tested quirks (2026-09-16): (a) **mermaid 11 ignores initialize()-time `fontFamily` for flowchart label painting** (only directives / per-widget config reach the rendered text) - so `buildPerWidgetInit` now injects the site font into EVERY diagram as a font-only `%%{init}` (the proven path); (b) **the upstream `$:/plugins/orange/mermaid-tw5/config` shadow tiddler ships `"fontFamily":"sans-serif"`**, and the wrapper's `buildSiteConfig()` whitelists that tiddler's values as user config - a code-level default in the wrapper is silently overridden by it. Any default that upstream ships as a data/shadow tiddler must be overridden with a same-title shadow in the patch plugin (user edits via the control panel still outrank shadows). Also: when gating edge-label contrast headlessly, measure the label's **effective backdrop starting at the element itself** - in html-label mode the themed backing is an inline background-color ON the span, so walking from `parentElement` skips it and misreports contrast.

- **Mermaid robustness hardening (2026-09-16, fixes the recurring "error for such things" class):** diagram sources are the #1 meatspace failure class - TiddlyWiki's parser and the markdown pipeline feed the widget entity nodes and typographic characters, and the upstream extractor (`rocklib.getScriptBody`) decodes only FIVE named entities, passing everything else through as literal poison text that mermaid's grammar rejects. The wrapper now owns the whole path with defense-in-depth: (1) `extractDiagramSource` walks the parse tree decoding ALL named + numeric entities, preserving line structure via `br`/`div`/`p`; (2) `sanitizeDiagramSource` normalizes BOM/CRLF/U+2028-9, strips zero-width + bidi + C0 controls, folds every Unicode whitespace variant to plain space, and maps typographic punctuation (U+2212 minus, smart quotes, primes, ellipsis, U+2010/2011) to ASCII - semantics-preserving for any diagram that already parsed; (3) a self-heal retry ladder: attempt 2 strips all `%%{...}%%` directives (the most common hand-edit failure), and `resetMermaidToSiteConfig()` re-initializes global config after ANY directive failure so a poisoned init directive can't break SUBSEQUENT diagrams on the page. Gate: `scratch/mermaid-robustness-gate.js` renders a poison battery through the REAL widget pipeline and asserts svg-or-graceful-error per case (a genuinely broken diagram still gets a readable error box - never a blank or a leak), plus a sanitizer unit suite mirrored from the wrapper. Two harness traps field-tested: the `rootWidget.makeChildWidget(transclude)` / `makeTranscludeWidget` patterns other gates use throw `parameter 1 is not of type 'Node'` inside element.js for the mermaid widget - use `wiki.parseTiddler` + `wiki.makeWidget` and render at root level (`widget.render(container, null)`), exactly TW's boot shape; and a bad-directive case must EXPECT self-heal (svg after directive strip), not an error box. Note gates run against the BUILT `src/lithic.html`: after editing wrapper JS you MUST rebuild (SOP, output at `wiki/output/index.html` then copy) or you will chase ghosts - the minified build renames identifiers, so verify propagation by grepping a distinctive STRING LITERAL (e.g. `directives-stripped`, `data-mmwrapver`), never a function name, and check the `src/lithic.html` mtime against your edit time when a stamp check suddenly reports false.

- **Merged numerals font (2026-09-16, supersedes the per-face experiment):** the site-wide Vollkorn face itself (`$:/lithic/fonts/vollkorn`) now carries KaTeX-derived digit outlines - `scripts/merge-vollkorn-digits.py` splices the ten digit glyphs from `KaTeX_Main-Regular.woff2` (both fonts TrueType-glyf, 1000 UPM, SIL OFL 1.1) into the embedded Vollkorn subset and rewrites the tiddler with a single-line base64 blob (wrapped blobs get rejected silently - see trap below). Digits therefore render with the LaTeX look EVERYWHERE (headings, dates, mermaid diagrams) with one font tiddler; letter outlines are untouched. The merged font is internally renamed "Lithic Serif" with OFL attribution (name-table rename required when modifying OFL fonts with Reserved Font Names), but the CSS keeps serving it as family "Vollkorn" so no stack changed: the wrapper/pyramid/config use plain `Vollkorn`, and `$:/lithic/fonts/katex-numerals` is now an inert stub (its old "Mermaid Numerals" face + body::after warm-up are gone; the stub must still ship so older standalones drop the leftover rules). Gate: `scratch/merged-font-gate.js` proves from RENDERED PAINT that digit-bearing labels' widths differ from the pre-merge subset (kept at `assets/fonts/vollkorn-pre-merge.woff2`, registered under a private reference family) while pure-letter labels match it exactly, and that no extra face is registered. Related trap: `document.fonts.check` without a text argument probes a space, so it vacuously passes for unicode-range-restricted faces; and a rebuild without `TIDDLYWIKI_PLUGIN_PATH` silently produces a plugin-less build that fails every render-dependent gate.

- **The launcher renders the same numerals amalgam as the wiki, compiled into the artifact (2026-09-21):** `launcher-ui/src/styles.css` used to `@import` Vollkorn from fonts.googleapis.com, so the desktop app needed the network for its own body text and rendered stock Vollkorn numerals. It now declares three `@font-face` faces (served under the existing `Vollkorn` handle, so no rule elsewhere changed) built by `scripts/build-launcher-font.py` into `launcher-ui/src/fonts/lithic-serif-{400,600,700}.woff2` from `assets/fonts/vollkorn-latin-vf.woff2` — Google's `latin` subset of Vollkorn v30, which is a VARIABLE font (wght 400-900, 231 codepoints) — with the ten digit outlines spliced from the KaTeX faces (Main-Regular at 400, Main-Bold above it), exactly as `$:/lithic/fonts/vollkorn` does for the wiki. Vite's existing `assetsInlineLimit: Infinity` base64s all three into `launcher.html` (245KB -> ~358KB), which is what makes the Tauri app's typography offline; a gate on the built file asserts zero non-`file://` requests. Three decisions worth not undoing: (1) **all three weights need real faces** because `:root` sets `font-synthesis: none` — an absent weight is not faked, it silently falls back to the nearest face, so inlining the wiki's 400-only subset alone would have lightened the h1, buttons and semibold labels; (2) **static instances, not the variable font** — the spliced CM outlines are static, so digits inside a VF would stay Regular while their letters thickened, which is most visible in the device-code box (`WXYZ-2345` at 700); (3) **do not reuse `$:/lithic/fonts/vollkorn`** — it is a 104-codepoint subset that lacks U+2026 and U+00D7, both of which the launcher paints (`truncateName`, `Starting…`), so shipping it would have introduced new fallback glyphs. Gate trap: **advance widths cannot prove a digit swap** — 3, 5, 6, 7, 8 and 9 coincidentally share Vollkorn's 500/1000em advance, so a swapped glyph is invisible to a width probe; compare rasterized outlines instead. Spliced digits execute inside the *host* font's hinting program, so they are not bit-identical to standalone KaTeX (measured 0-4px of difference) even though the outlines are the same — "closer to CM than to Vollkorn, for all ten" is the honest form of the claim (measured 288-526px against Vollkorn), and 98/98 non-digit glyphs are bit-identical to the source VF. Two harness traps: `document.fonts` is lazy, so an unused face reports `unloaded` and `check()` false until something uses it or you call `fonts.load` — a 700 probe without forcing the load silently measures the 400 face; and `document.fonts.check` without a text argument probes a space and passes vacuously. Refresh the source with the one-liner in the script's docstring (Google serves woff2 only to a modern UA). Not migrated: `launcher-fragments/document-head.html`, which still points at Google Fonts — that fragment belongs to the archived legacy launcher, not the shipped one.

- **What a launcher mount files itself under, and which mounts join the local edit chain (2026-09-21):** every mount has exactly ONE name — `resolveMountName` in `launcher-ui/src/scratch-editor.ts` — shared by its recent row, flat search cache, version history and dirty-state key. A Lithic document is normalized to `.lith`; scratch documents (`.md/.txt/.tid/.json/.ipynb`) and HTML monoliths keep the file's own name because they save back in place as themselves. Two real failures this prevents, both measured against the built artifact: (1) a monolith recorded under `normalizeLithName` while its row used the raw name left the row's history button permanently dead (nothing was ever recorded for `stock.html`) and handed search a cached-wiki key (`stock.lith`) that no file corresponds to — the ghost-row class again; (2) `bootLegacyHtml` recorded no save target, so the injected saver adopted the handoff the previously mounted wiki left in `sessionStorage` and wrote the monolith's page over that unrelated file (measured: a lith path, overwritten). Do not re-derive the name inline at a new call site; ask `resolveMountName`. Note `normalizeLithName` now has one definition in `legacy-saver.ts` (the App used to carry a duplicate).

- **Saved history and unsaved-edit recovery are separate policies, and an HTML monolith gets the first but not the second (2026-09-21):** a monolith keeps searchable cache + version history, recorded by the save path from what actually landed, so an edited monolith is findable and its row offers history. It opts out of `dirty_state_<name>` recovery (`tracksUnsavedEdits` false, `__LITHIC_ACTIVE_FILE_NAME__ = ""`) because a page may carry its own recovery through add-ons/plugins (a browser-storage saver, say) and the launcher must not interpose on what the page does with its own edits. That reasoning does NOT extend to `.lith` or scratch mounts — both record unsaved edits and prompt on the next mount, which is the behavior to preserve (verified end to end: edit a tiddler → `dirty_state_recipes.lith` → "Unsaved edits found" → Recover edits restores it and clears the record). Harness trap: navigating away from a mounted wiki that has unsaved changes raises a `beforeunload` dialog, and puppeteer's `page.goto` stalls outright until a `page.on('dialog', …)` handler accepts it.

- **A local-only Lith is offered a COPY into the covered folder, not a repository of its own (2026-09-22):** the (!) mark on a recent row used to set a per-row sync focus and open the connect dialog for that row's folder, so "this one is not backed up" was answered with "now you maintain a second backup" and the user's folder layout decided how many repositories exist. It now offers `Copy to Synced Dir` (`offerCopyToSyncedDir` → `copy_lith_to_synced_dir` in Rust): a copy into `syncedDirFor(recentRows(), backupRoots)` — the covered root of the newest covered row, which is the folder they have been working in — then `remember` moves the row to the copy (same file name, so the cached history and dirty-state keys stay valid) and a best-effort `git_sync_commit` makes the backup real, since a copy is not a save and nothing else would commit it. A copy, not a move, and a name collision in the destination is refused rather than overwritten: the other file may be a different Lith. The per-row `gitSyncFocus` state is gone with it — the dialog always means the Lith you have open or the newest one you opened. **Two template rules this exposed, both measured:** (1) the mark's condition must be written out in the markup (`showBackupStatus && localOnlyPaths.has(recentDiskPath(file) ?? '')`) and NOT asked of a helper function — Svelte re-evaluates a template condition when the variables it names change, and a call names none of them, so through `isLocalOnly(file)` the mark only appeared once something else rebuilt the row; a freshly painted list showed no marks at all and the copy offer was unreachable (the old function was deleted for this reason, and `tmp/sync-modal-copy-check.mjs` asserts the mark exists after a cold load); (2) "N of M recent liths backed up" now lives in the GitHub Sync dialog rather than under the recent list, because it is a statement about the backup and belongs beside the repository it describes, and the "Remote instances" group label above the bookmark rows is gone — the bookmark button itself says what those rows are.

- **The desktop GitHub sync acts on a DERIVED folder, so the dialog names it and a first connect is capped, counted and cancellable (2026-09-22):** the connect target is "the open Lith, else the newest recent row's folder" (`gitSyncTargetPath`), which means a Lith saved into `Downloads` silently aims the next connect at the *whole* Downloads folder — measured on the user's machine, `recents.txt`'s newest row was `C:\Users\temp\Downloads\tiddlers (1).lith`, so a connect tried to commit Downloads' 3,910 files. libgit2 hashed them inside one opaque call, so the modal sat on "Committing the folder's files…" for minutes with no count, no cancel, and a commitless `Downloads\.git` left behind. Four parts to the fix, none of which should be undone: (1) the dialog shows a `Folder  <path>` line, derived reactively from the same inputs ("Folder" label, full path in `title`, one truncated line) — a button since 2026-09-25, so the folder can be changed rather than only named, see the picker bullet below; (2) a first connect stages through `gitcore::stage_working_tree`, which enumerates `repo.statuses()` and therefore knows the exact count *before* hashing anything — over `FIRST_SYNC_FILE_CAP` (2,000) it refuses with the real number in the message (`This folder holds 3910 files. Back up the folder your liths live in.`) and the index untouched, and it removes the `.git` it created when a connect is refused or cancelled before anything was committed; (3) the modal gets "Committing N of M files…" (throttled at 400ms, total first) and a bare-text Cancel wired to `git_sync_cancel` → `gitcore::cancel`, which stops the staging walk per file, a fetch/push mid-transfer (`transfer_progress` returning false is the only mid-operation exit libgit2 offers) and the rescue loop per pulled file; (4) every stage, count and outcome is appended to `%LOCALAPPDATA%\Lithic\sync.log` (rotated at 1MB), because the Windows build sets `windows_subsystem = "windows"` and every existing `eprintln!` in this path goes nowhere. **Never use `Index::add_all`'s pathspec callback** — libgit2 passes NULL as the matched pathspec whenever the walk has no pathspec (always, here: an empty `paths`), and git2 0.21's `index_matched_path_cb` calls `CStr::from_ptr(NULL)`, which is a `STATUS_ACCESS_VIOLATION` (0xc0000005, measured) rather than anything a compiler reports; enumerating statuses costs one walk either way. Cancel scope matters too: the flag is process-global, so `git_sync_setup` clears it on entry and on every exit and `git_sync_commit_inner` clears it on entry — otherwise a cancelled connect aborts the next save's push and the icon reports a failed backup nobody caused.

- **The desktop sync target prefers an attachment over the derived folder, and only counts *finished* attachments (2026-09-22):** the target is derived — the open Lith, else the newest recent row — so a stray file decided where the backup went, which is the same class of failure the `Folder` line was added for. `git_sync_folder` (Rust) now answers what the launcher should act on, in this order: **(1)** the folder behind the derived path when Lithic already backs it up — the Lith you are looking at is the one you mean, and a wiki nested inside a synced folder resolves to the root that publishes it; **(2)** `Documents\Lithic` (or the running exe's folder, for a portable bundle) when a previous attachment left a repository there. Rule 1 wins on purpose: a folder you deliberately attached is not an arbitrary recent row. `None` means nothing is attached near either, and the launcher keeps what it derived, so a first connect in a folder of the user's own choosing still works. **The two rules ask different questions, and neither of them is the write test.** Rule 1 walks *up* from a file the user happened to open — possibly inside somebody's source checkout — so it demands the marker *and* a commit (`is_attached`): the marker alone is exactly what a killed or over-cap connect leaves behind (measured on this machine: `Downloads\.git` carrying `remote.origin.url` and no branch at all, which is why the stuck connect had shown "Connected repository" over a folder nothing had ever been pushed from), and preferring that is what would keep aiming the backup at the folder that failed. Rule 2 looks only at the app's own folders, where the marker must *not* be required — a Disconnect removes it, a stalled connect can lose it, and the user's real `Documents\Lithic` was measured with its commits intact and no origin at all, so requiring the marker there would have left the launcher aiming at a Downloads row (the exact bug this was asked for). Rule 2 therefore means "a repository a previous attachment left" = a commit, plus no `lithic.detached` flag (`is_left_repository`); `git_sync_disconnect` writes that flag and `sync_with_remote` clears it, which is also what keeps a Disconnected folder from being preferred straight back and leaves the folder you are working in as what the dialog proposes next. Coverage and every automatic write still ask `is_managed_dir` (the marker alone), because a save does commit through a marker-only folder: the questions are different, and the write path keeps its test. Sync commands now take a file *or* a folder (`sync_dir_of`), because the launcher hands over the folder it resolved and a rebuild hands over whichever it holds. Frontend half: `resolveSyncFolder` carries a token so a stale answer never lands, and the reactive subject is spelled `filePath ?? newestRecentPath(recentFiles)` — naming `filePath`/`recentFiles` directly, because a reactive statement tracks the variables it *names* and a helper call names none of them (the same Svelte trap the local-only mark hit; the comma-operator spelling of this is rejected by svelte-check as an expression with no side effects). The escape hatch is no longer only Disconnect: the dialog names the folder it acts on, and since 2026-09-25 that line is a picker whose answer outranks both rules (see the bullet below).

- **The folder a backup acts on is now the user's to choose, and the choice rides in `recents.txt` (2026-09-25):** the `Folder` line was derived and read-only, so the only way to move a backup was to Disconnect first — a strange thing to require of somebody who keeps their liths somewhere else. It is a **button** now, opening the OS folder picker (`pick_sync_folder`, Rust; async because Tauri 2's blocking pickers must not run on the main thread, the same rule the file dialogs follow). It opens on the folder in force, so changing one is a step from the current answer, and the line carries a `Change` hint plus the full path in the path span's `title` (the line ellipsizes; the tooltip is how a person reads which folder this really is). **The pick is recorded by Rust, not by the page, and it rides in the ONE file that already exists beside the exe** — `recents.txt`, as a `sync-folder=` settings line beside `dismissed=1` and the paths. A third sidecar was offered and declined, and so was merging the credentials vault into that file: the vault is a PIN-encrypted container whose every write rewrites the whole ciphertext, so one file would make each recents save a vault write (a crash mid-write costs the passwords, not the history) and would let a hand-edited plaintext path list corrupt a file with no recovery. Two sidecars, and that is the reason there are not three. **The line is spelled relative to the exe's folder when the folder lives under it (`.` when it *is* that folder) and absolute when it does not** — the rule the recents lines above it already follow, and the whole point of it: a thumb drive gets another letter on the next machine and `sync-folder=liths` still names the folder beside the executable, where an absolute line would name a path that is not there. A recorded folder that is *not* on this machine is not an answer (`chosen_sync_folder_in` asks `is_dir`) and falls through to the automatic rules, so a bundle copied without its folder still opens on a usable one. Every writer of that file now has to leave the line alone: `read_recents_in` skips it (it is not a row), `write_recents_in` re-reads and re-emits it so a recents save cannot forget the choice, `set_install_dismissed` filters it out of the paths it rewrites, and `set_sync_folder_in` replaces only that line. The resolution order is now: **the user's pick**, else the folder behind the derived path when Lithic already backs it up, else a library folder a previous attachment left a repository in — and the pick is a separate function from `preferred_sync_folder` on purpose, because that one is Lithic working the folder out from evidence and this is the user having said so. Frontend half: `git_sync_folder` answers `{folder, overridden}` (the dialog has to know whether the folder is a choice it can offer to give back), a pick is **re-read** rather than assumed (`resolveSyncFolder` then `refreshGitSyncStatus(true)`, so the repository the dialog is showing cannot outlive the folder it belonged to), and `Use the automatic folder` (`clear_sync_folder_override`) is drawn only while an override is in force. Verified by Rust tests (a pick outranks both automatic rules, a missing pick does not, the marker survives a recents rewrite and never becomes a row, clearing takes only that line, and the `.`/relative/absolute spellings round-trip) and by two harnesses: `scripts/test-puppeteer-launcher.mjs` drives the desktop dialog with a mocked bridge and asserts the line is a `BUTTON` labelled `Folder` with a `Change` hint, that clicking it asks `pick_sync_folder` exactly once and re-reads the folder, that the way back is offered only after a pick and is one command — **with the teeth proved by deleting the re-read and watching that section fail** — and the gallery's `771-github-sync-folder` pane photographs the picked state beside the automatic one. **What a fresh download does was the hole left in that** (same day): with no recents, no open Lith and no repository anywhere, `git_sync_folder` answered `None`, `gitSyncFolder` was `''`, the row was hidden *and* `!gitSyncActivePath()` replaced the dialog's whole body with "Save a Lith to disk first, since sync backs up its folder." — a dead end, because the picker lived inside the guard that was false. Three parts, all of them load-bearing: (1) the row is drawn whenever the app is the desktop one, with `No folder yet` where the path would be (dimmed, oblique, no `title` — there is no path to carry) and `Choose` as the hint, so the picker is the way out rather than a control nobody can reach; (2) `proposed_sync_folder` answers a last-resort folder, and only where the program's own folder is *evidence* rather than an accident of where it was unzipped — the folder the app installs itself into, or a bundle that already holds a `.lith` — else the install folder when it is on disk, else nothing. That restriction is the point: the first connect commits what it finds and a repository that exists is what every rule above prefers from then on, so a Downloads folder or an extracted zip must never be proposed. It rides in `answer_folder`, conditional on the launcher having no subject at all, so a derived path still outranks it and a pick outranks both; (3) the "save a Lith first" line became a reactive `gitSyncNoTarget` instead of `!gitSyncActivePath()` asked in the markup, because Svelte only re-runs a block when a variable it *names* changes and a function call names none — so the line stayed on screen after a pick from the empty state (measured, then fixed; `gitSyncFolder` above it is a variable for the same reason).

- **A recents row never carries a document's body, and a full store never costs a mount (2026-09-25):** the row mirror in `localStorage` (`lithic-recent-liths`) wrote each row's `text` verbatim, and the budget there is about 5 MB measured (`4 MB` fits over `file://`, `5 MB` does not) — so a 10 MB Lith failed **its own mount** with `QuotaExceededError`, surfacing as `Could not open Final_Semester.lith: Failed to execute 'setItem' on 'Storage'…` on a hosted instance and, through `mountTauriPath` -> `mountWiki` -> `remember`, on the desktop too. The legacy launcher never did this: `launcher-fragments/runtime.js` keeps `recentFiles` in IndexedDB as handles plus `tauriPath` and no text at all. `persistRecentRows` now mirrors a row's text only where it is the row's last copy — a row with a path is re-read from disk or the server, and a Lith's content is already in the search cache the mount's own saver writes — and only under `RECENT_TEXT_LIMIT` (512 KB), because a body big enough to matter cannot fit beside the rows that name it and a write that cannot fit is a failed write. The write itself may never throw into a mount: a store that refuses the first attempt is retried with the texts dropped, so what is left is the list of names and paths, with the in-memory list as the copy that always stands. `openRecent` gained the matching else branch, because a dropped body leaves a row that would otherwise answer a click with nothing (`No file path recorded. Open it once via Mount to re-link it.`, the wording the tauri branch already used).

- **The folder picker belongs to setting the backup up, and Disconnect forgets the pick (2026-09-25, same day):** the connected dialog offered `Change` over a backup that was already running, which put a folder picker in front of a repository that was not going to move with it. The line is now the picker only while a backup is being set up — the Connect screen, the device-code step it rides on, and the repository choice that follows, every screen up to the one that commits — and the connected dialog names the same folder read-only, in the identical place, as a `<div>` rather than a disabled button because nothing there is a control. Three things make the code step work as the picker's main home and none of them needed loosening: `startDeviceAuth` clears `gitSyncBusy` in its own `finally` as it spawns the poll, so the row is already enabled while GitHub is waited on; `chooseSyncFolder`'s status re-read cannot yank the view because `refreshGitSyncStatus` skips applying a view while the flow is `connecting`; and the poll answers `pending` forever in the harness, so the step is a place to stand. - **The shim has a command wire, and the gate exists before anything is behind it (2026-09-30, later that night):** the approved backend work needs an endpoint, and this pass lands the endpoint and nothing else. **Why a wire at all:** a browser hands a page a file's *contents* and never where the file is (a `FileSystemFileHandle` deliberately exposes a name and no path, and `<input type=file>` gives a fake one), so native file access, the GitHub backup and the credential vault can only be done by the process serving the page. **Why the gate comes first rather than with the first command:** CORS stops a hostile page from *reading* an answer, not from causing the effect, and a loopback POST is a simple request unless it is JSON, so the write happens whether or not the page can see the reply. Retrofitting the checks onto a wire that already writes files, runs git and lends a stored credential is the expensive direction, so they are here with nothing to protect yet. **What the gate is:** `POST /__lithic/command` only, because a state-changing `GET` is the one shape a hostile page can cause with no preflight at all; `Origin` exactly `http://127.0.0.1:<port>`; `Host` exactly `127.0.0.1:<port>`, which is what a name resolving to loopback cannot present because the browser still puts the attacker's name in the header; `Sec-Fetch-Site: same-origin`; the token; `application/json`; and a 64 KB body cap read before the body is buffered. Every failed check answers the same one message, so the wire cannot be probed, and no CORS header is ever sent, so a request that somehow got through still could not be read. **The secret is minted per launch and never persisted:** `new_token()` is 32 bytes from the OS entropy source through `getrandom` (the standard library has no CSPRNG, and a token built from the clock and the process id is guessable by exactly the kind of page it exists to keep out), hex, injected by `inject_token_meta` as `meta[name="lithic-shim-token"]` into `src/launcher.html` and into no other file, and compared over every byte so a wrong token's timing says nothing. It is injected by a pass of its own rather than as a third tag inside `inject_server_meta`, so the proven browser-only and build-tag rules and their tests are not disturbed: both passes find the same insertion point (an injected meta neither opens a `<script>` nor closes the head), and a test pins all three tags contiguous immediately before the real `</head>` on the artifact. **Nothing is behind it:** `ping` answers `{"ok":true,"result":{"shim":true}}` and any other command answers `{"ok":false,"error":"unknown-command"}` at 200, so reachability is provable without exposing a capability. **The launcher's side is `shim-command.ts`** (`readShimToken`, `shimCommand`, the `fetch` injected and every failure returned as a value), shaped like `server-git-sync.ts`; `App.svelte` reads the secret once and probes with `ping` at boot, recording the answer as `data-shim-backend` on `<main>`, which is the reachability proof and the hook the next phase reads. **Two small dependencies arrived with it**, and the crate's docs and `shim/Cargo.toml` say why: `getrandom` for the secret and `serde_json` for the wire in both directions. The release binary is 286 KB after `lto`/`strip` (246 KB before), so the AppImage arithmetic is unchanged and the 12 MB ceiling the user set is not close. ** **Left open and recorded honestly:** the token guards the *page* boundary, not a sandbox. A local program can read `GET /src/launcher.html` and lift the secret, but a local program on this machine can already write the same files and run the same git without the shim, so the secret's job is per-launch revocation and a hostile-page boundary rather than isolation from the machine. Nothing sends a command yet, so `shimBackendUp` is recorded and read by nothing; native file access is the phase that consumes it.

- **The shim's command wire has native file access behind it, and the chooser is the desktop's own (2026-09-30, later that night):** this is phase 2 of the approved backend work, and it is the first capability the gate ever protected. **Why a chooser had to be built at all:** a browser hands a page a file's *contents* and never where the file is, so "open a Lith" and "save it back where it came from" are both impossible from the page alone.
