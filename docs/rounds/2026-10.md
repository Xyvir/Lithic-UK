- **The shim reads a synced folder's marker straight out of `.git/config`, so the offline half of the git sync needs no git library at all (2026-10-01):** this is phase 4 of the approved backend work, started at the end that needs no dependency so the dependency that is coming can be chosen on purpose rather than in a hurry. **Why the surface splits in two at all:** the desktop app answers every one of these questions through libgit2, because a process that already links a git library should use it, and the shim is the process that must not: the whole reason `lithic-shim` exists is an artifact the size of the payload it serves, and a linked libgit2 plus a TLS stack is the one thing that ends that. So the split is by what an answer needs. **Reading a repository is a file read.** The only question the launcher asks about a folder it already has is whether Lithic manages it, and Lithic marks every folder it manages with an origin URL it wrote itself (`https://oauth2:<token>@github.com/owner/name.git`, the same shape `deploy/github-sync.sh` writes for self-host), which lives in `.git/config`, which is text. `shim/src/git.rs` answers three commands from that one file and nothing else: `git-status { path }`, shaped exactly like the desktop app's `git_sync_status` (or `null`, and the null covers both a folder outside a repository and a repository whose origin Lithic did not write, because the launcher draws the same grey for either); `git-coverage { paths }`, one answer for a whole recents list with an uncovered path simply absent, so a row is never told apart from an unbacked one by a null; and `list-folder-liths { path }`, the flat newest-first `.lith` listing the re-index wants, capped at the same `REINDEX_LIST_LIMIT` of 500. All three accept a file or the folder holding it, for the same reason the desktop app's `sync_dir_of` exists, and all three walk *up* from a path when asking whether a folder is managed, because a commit is recursive and a wiki in a subfolder really is published by the repository at the root. Two rules came over from the desktop app whole rather than being re-derived: the marker is the `oauth2:` in the URL, which is what keeps a git folder the user made themselves out of every automatic commit and push, and a URL that carries the marker is managed even when it cannot be read, so reconnect is the repair rather than a refusal. **What the reader is, and what it deliberately is not:** a subset reader for the one shape `.git/config` uses for a remote (sections in `[name "subsection"]` form, `key = value`, comments stripped only outside quotes because a `#` can sit inside a value, git's case-insensitive sections and keys with an exactly-matched subsection, and the double quotes git puts around a value with a leading or trailing space), not a general config parser. `include`/`includeIf` are unhandled and a `.git` that is a *file* rather than a folder (a linked worktree or a submodule) is not a managed folder, both named in the module and safe in the direction they fail: Lithic writes neither. One measured divergence from the desktop app and it is a fix rather than a drift: `Path::new("notes.lith").parent()` is `Some("")`, and joining `.git` onto that reads a config relative to the process's working directory, which is a folder nobody named, so an empty parent is filtered. **The smallest OpenSSL is a choice between two stacks rather than between two versions, and that is the decision recorded here.** libgit2's HTTPS transport is a compile-time backend choice rather than a bundled TLS library, and on the Linux it can be OpenSSL or mbedTLS (a platform stack on Windows and macOS, neither of which an AppImage can use), but `libgit2-sys`'s build script only ever defines `GIT_OPENSSL` there: its `https` feature pulls `openssl-sys`, so OpenSSL is the only Linux backend this crate can actually reach and it is not optional the moment the sync talks to GitHub. Two ways out were looked at and rejected rather than missed. mbedTLS is the smaller library and libgit2's own stream glue for it is compiled in, but nothing in `libgit2-sys` can select it, so reaching it would mean forking a build script or linking a system libgit2 built that way, the second of which throws away the portability the AppImage is for. And a custom transport is genuinely possible, since the crate exposes `transport::register` with `SmartSubtransport` (its own workspace ships `git2-curl` doing exactly this over libcurl), which would put the git byte pump on ureq and rustls and remove OpenSSL entirely. That is the real alternative and it is not free: we would own the smart HTTP protocol, its version negotiation and its credential handling, which is the most protocol-sensitive part of the whole feature, to save a statically linked piece of C that a mature crate already builds and tests. It stays on the table as a later measurement rather than being the first shape. What follows from the crate's Cargo.toml is also worth knowing for the dev loop: `openssl-sys` is only a dependency under `cfg(all(unix, not(target_os = "macos")))`, so on Windows this feature means WinHTTP and needs no OpenSSL at all, which is why the only thing a Windows checkout of the shim would need to build these commands is a C compiler for libgit2 itself. The device flow and the REST calls need an HTTP client of their own, and the tempting answer for that is rustls, which would ship a second TLS implementation (rustls, its crypto provider and a root store) beside the OpenSSL libgit2 already requires. So there will be exactly one: the vendored OpenSSL, statically linked, with `git2 = { version = "0.21", default-features = false, features = ["https", "vendored-libgit2", "vendored-openssl"] }` and `ureq` on its `native-tls` backend, which on Linux is the same `openssl` crate over the same `openssl-sys`, so one build of OpenSSL serves both. Vendored rather than the system library, on the argument that an AppImage must not depend on the host's `libssl` and that static linking lets the linker drop the OpenSSL objects nothing calls. **That half was reversed the same day and the reversal is the entry at the end of this file: the TLS is the system's, and only `git` is packaged in.** **On version, smaller is not better here:** OpenSSL 1.1.1 is the smaller artifact and is end-of-life, so it is the wrong kind of small for a binary that carries a GitHub token, and the smallest *maintained* OpenSSL (the 3.x `openssl-src` builds) is the floor. **None of it was in `Cargo.toml` in that pass, on purpose**, because the release job is the only place a Linux build of a vendored C library is ever exercised, so the lines waited for the code that uses them. They are there now, and what happened when they landed is the next entry. ** **Left open and recorded rather than implied:** nothing on the launcher side is wired to these three commands yet, so a shim still shows no sync UI at all, and the gate the launcher needs (`hasLocalSync()` where the git gates currently read `mode === 'tauri'`) plus the routing of `git_sync_status`/`git_sync_coverage`/`list_folder_liths` through the wire is the next slice; `git-folder` is not implemented, because it answers from the sidecar and the library folders the desktop app owns and the shim has no equivalent of yet; and the writes need the job-and-poll model the desktop app already has (`git_sync_setup` returns at once and the launcher polls), because the shim's connection handler writes with a 30 second timeout and a first clone or a large push runs past it.

- **The shim runs the GitHub device flow itself, and the dependency set the OpenSSL decision chose is now in the manifest (2026-10-01, same day):** the four lines above are in `shim/Cargo.toml` (`git2` with `https` and `vendored-libgit2`, and `ureq` with `native-tls`; `vendored-openssl` and ureq's `vendored` were in this first landing and came straight back out the same day, see the last entry), and `shim/src/github.rs` is the half of the sync that uses the HTTP client. **Why the shim has to run the flow at all:** `https://github.com/login/device/code` answers with no `Access-Control-Allow-Origin` header at all, so a browser refuses the request before it leaves, which is the same reason self-host proxies these calls through its CGI handler and the desktop app makes them from Rust. `api.github.com` does allow cross-origin reads, so the two REST calls could have been made from the page, but running all four here means one token path and one place the credential is handled, which is worth more than the two calls it saves. The commands are `github-device-code`, `github-device-poll { deviceCode }`, `github-list-repos { token }` and `github-create-repo { token, name }`, each mirroring the desktop app's own command of that name down to the shape of the answer, because `github-device.ts` decodes both backends and must not have to care which one answered. The poll's normalization is the part that matters: `authorization_pending` and `slow_down` are **successes** (`{pending:true}` and `{pending:true, slow_down:true}`) rather than failures, since they are exactly what GitHub says for the whole time a person is still typing the code. **One addition to the wire was needed and it is small:** `failed_with(code, detail)` answers `{"ok":false,"error":"github","detail":"..."}`, so the code stays a code (the launcher can still tell a refusal that came from GitHub from one that came from the wire) while GitHub's own sentence rides beside it in `detail`, which is what the desktop app already shows the user. The transport is a single shared `ureq` agent, blocking, with two settings that are load bearing: `http_status_as_error(false)`, because GitHub reports an expired device code and a rate limit as a 4xx whose *body* says which and the poller has to read it rather than a bare status; and a 30 second cap, which is the shim's own patience rather than a preference, since the connection thread waiting on the answer has a 30 second write timeout. **What the dependency landing actually measured, on this Windows checkout:** the whole set compiles with **no extra toolchain**, libgit2's C sources included (`cc` finds MSVC on its own), `native-tls` resolves to SChannel there, and no OpenSSL is built at all, because `git2`'s `https` means WinHTTP on Windows and its `openssl-sys` dependency is declared only under `cfg(all(unix, not(target_os = "macos")))`. That is why `vendored-openssl` can be asked for unconditionally without breaking the Windows dev loop, and it was checked with a throwaway crate in `tmp/` before the manifest was touched. Two findings worth keeping: `ureq`'s stable `native-tls` feature also pulls `webpki-root-certs`, a bundled copy of the Mozilla root program, while this path verifies against the platform trust store and never reads it, and `ureq`'s `native-tls-no-default` is the feature that drops it but sits on ureq's unstable list, so the extra data blob is recorded in `Cargo.toml` as one word away rather than bought with a build that depends on an unstable feature name. And `git2` is declared **before** the code that uses it, deliberately: the release pipeline now exercises the Linux build of vendored libgit2 and vendored OpenSSL from this commit, so a toolchain problem surfaces as a dependency problem with no git code in the way, rather than in the middle of the clone-and-push module. ** **Left open, in the order the remaining work falls:** the launcher is still not wired to any of these, so a shim still shows no sync UI and no setup flow; the git writes (`git-setup`, `git-commit`, `git-heartbeat`, `git-reauth`, `git-disconnect`) and the job-and-poll model they need are the next module; and where the token comes to rest is git's own credential helper rather than a file this process writes, which is the third approved decision and is not implemented yet either.

- **The TLS goes back to the system and only `git` stays packaged in, because `libssl` was already on every machine this ships to (2026-10-01, later the same day):** the vendoring decision recorded two entries up was reasoned from an AppImage rule (do not depend on the host's libraries) rather than from what this particular host library is, and the owner corrected it in one line: every Linux that has `ssh` or a package manager already has `libssl`, so a dynamic link to it costs this artifact **nothing**, where a vendored copy is a second copy of a library the machine is already patching on its own schedule. That is the whole of the change and it is two feature removals: `git2` loses `vendored-openssl` and `ureq` loses `vendored`, so `openssl-sys` now probes the system at build time and links `libssl` at run time instead of compiling OpenSSL from source. **`git` is the deliberate exception and stays packaged in.** `vendored-libgit2` is untouched: libgit2's C sources (with its bundled llhttp, xdiff and PCRE2) are still compiled on the runner and linked statically, because the alternative is shelling out to whatever `git` the machine happens to have, a program whose version and configuration the launcher cannot control and whose absence would be one more thing a person has to install. So the split is by what the library is: a TLS implementation is infrastructure the machine's package manager already owns, where the git object model is a thing this application has to have and cannot borrow. **What it costs and what it asks for.** The odd dynamic-link risk is now real and is accepted rather than hidden: a binary linked against OpenSSL 3.0 will not run on a distribution that still ships 1.1.1, and the shim is built on `ubuntu-22.04` precisely so the linked ABI is the lowest 3.x a current distribution has. The build machine needs the headers, which the release job did not install for this job before now: `.github/workflows/desktop-release.yaml` gained an `Install System Dependencies` step (`libssl-dev` and `pkg-config`) in the `build-shim-appimage` job, and that is the first system package that job has ever installed, next to a comment saying why it is not the GTK/WebKitGTK posture it rejected. Windows and macOS are unchanged and need no OpenSSL at all: `git2`'s `https` is WinHTTP and SecureTransport there, `openssl-sys` is not even a dependency of this crate on Windows, and `native-tls` is SChannel and Security. ** **Left open, and now the one thing about this that is unverified:** the Linux half of this change has not been compiled anywhere on this machine, because `openssl-sys` is not in a Windows build at all, so the probe of `libssl-dev` on the runner and the dynamic link are argued from the build script and from `ubuntu-22.04`'s known OpenSSL 3.0 rather than observed. It is exercised by the next release build, and a `cargo check` under the WSL Ubuntu on this machine would settle it before that if the toolchain is wanted there.

- **A shim now reads a folder's backup state, and the launcher was taught that this is not the same question as "is this the app" (2026-10-01, same day):** step 1 of the five that remain, and the first time any of the shim's git surface is reachable from the page. The whole change is one idea: **`mode === 'tauri'` was standing in for two different questions**, and only one of them is about the app. *Can a process on this machine answer a question about a folder:* the desktop app can, and so can a shim, whose wire walks up from a path to the marker in `.git/config` (`shim/src/git.rs`). *Can a process on this machine change a repository:* still the app alone, because the shim has no writes until the libgit2 module lands. So `App.svelte` grew `hasLocalSync = mode === 'tauri' || shimToken !== null`, and it gates **reads only**. Gating a write on it would put a button on screen that answers "Tauri API unavailable" on a shim, which is worse than the button not being there. **What that turns on for a shim, and where it shows:** the backup coverage read (`git_sync_coverage`) now goes through a shim's wire as well as through Rust, which puts the per-row unfinished mark and the non-backed-up header's folder into a shim's recents list for the first time; `showBackupStatus` follows the same gate, which is what makes the marks appear at all; the rebuild's folder walk (`list_folder_liths`) and the per-wiki read it indexes (`read_lith_path`) both answer through the wire, so a shim's Rebuild Recents control now lists and indexes a backed-up folder rather than doing nothing; and both call sites went through one routing function each (`readGitCoverage`, `readFolderLiths`, `readDiskWikiText`) rather than a mode branch at each of the four places that wanted them, because a branch per call site is a branch that drifts. **Three things were deliberately left where they were, and each has a reason rather than an omission.** The header's sync control and the whole dialog stay the app's and an instance's: every action inside the dialog is a write (`git_sync_setup`, `git_sync_commit`, `git_sync_disconnect`, `git_sync_cancel`, `pick_sync_folder`), so a shim's dialog would be a dead end until step 2, and a status light that cannot be acted on does not exist as a control yet either. `git-status` is built and tested at the wire and has **no consumer** in the page, because its only reader is that icon: the icon's fold calls `runGitSyncHeartbeat` when it sees a connected repository, and a heartbeat is an ls-remote, which is a write-side operation the shim does not have. So the status read arrives with the icon in step 2, and `shimGitStatus` ships in `shim-git.ts` with tests ahead of its caller, the same way `shimList` did in phase 2. And the "Copy it into the synced folder" offer inside the history dialog is now gated to the app outright, because the coverage read that reveals it on a shim would otherwise lead to `copy_lith_to_synced_dir` and a commit, neither of which a shim can answer. ** **Left open, unchanged from the five-step list:** the git writes and the job-and-poll model, then `git-folder`, then the token at rest in git's credential helper, then routing the four `github-*` commands so the device flow is reachable at all.

- **The shim can write a repository now, and anything slow answers with a job instead of a timeout (2026-10-01, same day):** step 2 of five, and the point at which `git2` stopped being a declared-but-unused dependency. `shim/src/gitwrite.rs` is a port of the desktop app's `src-tauri/src/gitcore.rs`, deliberately close to it rather than a fresh design: libgit2 over the system `git` for the reason that file already argues (a spawn depends on `PATH`, a Windows "Git from Git Bash only" install breaks it silently, and a shim is a download on a machine nobody vetted for it), `main` as the branch on both sides, the `lithic.detached` marker in the repository's own config, `origin` written as `https://oauth2:<token>@github.com/owner/name.git` with the standard fetch refspec so a user running git by hand in the folder sees what they expect, `core.autocrlf` pinned off in repositories Lithic creates so a Lith's bytes survive the round trip, `user.name`/`user.email` filled in only where the machine has none, and the same "nothing to commit is a no-op" rule so a save that changes nothing cannot pile up empty commits. **Two details were carried over because they were learned the hard way, and neither is obvious from the API.** Staging enumerates `statuses()` and calls `index.add_path` per entry rather than using `Index::add_all`, whose pathspec callback gets a NULL matched-pathspec whenever the walk has no pathspec (always here) and segfaults in git2 0.21's trampoline; and the file cap of 2000 is checked against that enumeration *before* anything is hashed, so an oversized folder is refused in milliseconds with the index untouched and with the real number in the sentence. **The job model is the genuinely new part, and it exists because of this server rather than because of git.** The shim serves one thread per connection with a thirty second write timeout, and a first clone or a large push runs past it, so the page cannot be left waiting on one request. `git-setup` and `git-commit` therefore answer `{ "job": id }` immediately and do the work on a thread of their own, `git-job { id }` answers `{state, stage, error, result}` with `state` one of `running`/`done`/`failed`/`cancelled` (plus `unknown` for an id from a previous launch, answered rather than refused so a late poll is not an error the page renders), and `git-cancel { id }` sets a flag the work checks per staged file and on every transfer progress callback, which is the only exit libgit2 offers once a transfer has started. **Cancellation is per job, and that is a deliberate fix rather than a variation:** the desktop app has one flag for the process, which once let a cancelled connect abort the next save's push, because the two shared it. A job here carries its own. The three commands that cannot be slow stay synchronous (`git-reauth`, `git-disconnect`, both of which only edit config), and so does the fourth thing the icon needs. **The heartbeat is not a git operation at all, and reading the desktop app is what showed that:** `git_sync_heartbeat` there is one authenticated GET against `api.github.com/repos/{owner}/{name}`, reading the status, the `x-ratelimit-remaining` header and the token's `permissions.push`, and turning them into the launcher's own verdict words (`ok`, `readonly`, `auth`, `throttled`, `missing`, `offline`, `malformed`, `unmanaged`) with the one sentence its tooltip shows. The shim's `git-heartbeat` is that same probe in `github.rs`, unwrapped from a job because one request is well inside the write timeout, and it never answers a failure: being unreachable is a verdict, not a command that went wrong. **What a connect does, stated because it is where the care is.** An empty folder is cloned. A folder with files and no repository is initialised, the remote's files that are missing locally are rescued onto disk (adds only, never overwriting what the user has, and the add-only rule is what makes it safe), the folder is committed and pushed with the remote branch rewound when it had one, which is safe precisely because the rescue ran first. A folder that is already a repository is re-pointed, committed and pushed **without** force, so a remote that has moved on is refused with a real error rather than overwritten. That last choice is a deliberate difference from the desktop app's union merge, which is the one piece not ported: this never destroys remote history, and it is named in the module as the thing to fill in rather than presented as parity. ** **Left open:** nothing on the page calls any of it yet, because the icon and the dialog are the next change and they need the poll loop rather than a single await; `git-folder` is still absent, so the dialog's folder line is the derived one only; the token still has nowhere to rest; and the four `github-*` commands are still reachable only from the wire.

- **A shim answers which folder a backup acts on, and the person's own pick lives in a file of its own (2026-10-01, same day):** `shim/src/syncfolder.rs`, three commands (`git-folder`, `pick-folder`, `clear-folder-pick`) and the one line they share. The desktop app keeps the pick as a `sync-folder=` line inside `recents.txt` beside its executable, spelled relative to the bundle where it can be; a shim has no sidecar and no bundle to spell against, so the equivalent is one line in a file of its own under `app_data_dir()` (`$XDG_DATA_HOME/lithic/sync-folder`, falling back to `$HOME/.local/share`), and the path is stored exactly as it was picked. Deliberately *only* the pick: a shim has no recents list and no install offer to carry along, so there is nothing a rewrite could disturb, and that is the desktop app's own reason for reading the line back rather than taking it as an argument, reduced to its simplest form. **The resolution order is the desktop app's minus the two rules that need an installation to ask:** the recorded pick when it is still a directory on this machine, else the managed repository above the `derived` path when one covers it (the Lith you are looking at is the one you mean), else the folder the `derived` path names. What is missing on purpose is the library-folder rule and the proposal, both of which are questions about where an *installed* app keeps its liths. `overridden` is the desktop app's own rule verbatim: a pick that is no longer on this machine falls back to the derived folder and reports `overridden: false`, because nothing recorded is in force and the dialog has no override it can offer to undo, so a drive that is not plugged in hands the next setup back to the automatic rules rather than naming a path that is not there. **The chooser is the same three programs in the same order as `pick`, with a dialect of its own rather than a shared argument list:** no chooser has a switch that turns a file dialog into a directory one (`zenity` gets `--directory`, `kdialog` gets `--getexistingdirectory` outright), so sharing `picker_args` would have meant branching on every argument anyway. A cancelled pick is `{ folder: null }` rather than a failure, `no-picker` is a machine with no chooser at all, and the pick is recorded as part of the same call the way the desktop app's `pick_sync_folder` does, so a caller re-reads `git-folder` rather than trusting the path it was handed. **One piece of plumbing changed to make this possible and is worth knowing about:** `app_data_dir()` is no longer `#[cfg(any(target_os = "linux", test))]` — the folder command is dispatched on every platform and the test run on a non-Linux machine has to compile it — and the folder pick file is the first thing under that directory that is the shim's *own* state rather than the browser profile below it. **A disconnect forgets the pick, and the shim's does too.** The pick was made for the backup that just ended, and the dialog offers the picker only while setting one up, so a folder recorded for a gone backup would be a choice nobody can see or undo; `git-disconnect` clears it best-effort after marking the folder detached, exactly as `disconnect_sync_folder` does in Rust, because failing to rewrite a preference must not read as a failed disconnect. **

- **The sync icon and dialog are on for a shim, and every sync call goes through one helper per question rather than a mode branch per call site (2026-10-01, same day):** the last two of the five steps, plus the prerequisite the list implied — a shim that shows no dialog at all was not going to demonstrate anything. **`hasLocalSync` now means both halves.** The previous entry gated only the reads, on the argument that a write a shim cannot answer is worse than no button; that argument expired the moment `git-setup` and the rest landed, so the header's cloud button, `resolveSyncFolder`, `refreshGitSyncIcon`, `runGitSyncHeartbeat`, the folder line's two halves and the dialog's Stop control all read `hasLocalSync` now. What bounds a shim is no longer this flag but the *document*: the shim injects its per-launch secret into `launcher.html` alone, so the wiki page a saved Lith opens as has no wire to reach, and the save-time commit therefore stays on the desktop app's bridge (`legacy-launcher-runtime.ts`) — recorded in `hasLocalSync`'s own comment so the next person finds the boundary by reading rather than by measuring. **The routing is by question, not by command.** `readGitFolder`, `readGitStatus`, `readGitHeartbeat`, `pickSyncFolder`, `clearSyncFolderOverride`, `githubDeviceCode`, `githubDevicePoll`, `githubListRepos`, `githubCreateRepo`, `gitSetup`, `gitReauth`, `gitDisconnect` and `cancelGitSync` each branch on `mode` inside, and each call site kept its own name. That is deliberate rather than cosmetic: the launcher's decoding is shared between the two backends and the *shapes* have to agree (`github-device.ts` must not care which side answered), and a `mode === 'tauri'` ternary at each of the dozen call sites is a branch that drifts. The one place the shapes genuinely differ is the job model, and `runShimSyncJob` is where that difference stops: it polls `git-job` every 500 ms, reports each stage into the dialog's own progress line, keeps the id in `gitSyncJobId` so the modal's Stop can reach it, and hands back the desktop app's answer shape so the flow around it needed no other change. A cancelled job is not a fault: it raises one line (`copy.dialogs.gitSync.cancelled`, added in all four locales) rather than a code the user would have to read. **Two smaller things the wiring exposed.** The shim's `pick-folder` records the choice as part of the same call, so `chooseSyncFolder` re-reads `git-folder` instead of trusting the path it was handed, exactly as the desktop app's own comment says. And the shim's Stop is per job (`git-cancel { id }`), because its commands are stateless and several could in principle be running, where the desktop app's is one process-global flag — the same divergence `gitwrite.rs` already made for the reason recorded there (a cancelled connect once aborted the next save's push). **One drift bug from the previous pass was found by walking the callers rather than by a test, and it is fixed here:** `indexLithsHere` guarded its per-file read with `mode === 'tauri' ? readDiskWikiText(entry.path) : ''`, which made a shim's rebuild index **nothing** from disk even though `readDiskWikiText` had been taught the wire the pass before. The guard is gone and the helper's own branch is the whole of the question; the lesson is the one the routing helpers exist for, which is that a mode check *outside* a helper that already checks the mode is a check that silently wins. **

- **The token at rest is already where the desktop app keeps it, so the shim adds no credential helper (2026-10-01, same day):** the fourth of the five steps was "token at rest via git's credential helper", and measuring it changed the answer rather than the code. The reasoning for the helper was that the shim should not author a secret file of its own; the measurement is that it does not and never did. A managed folder's origin is `https://oauth2:<token>@github.com/owner/name.git` in `.git/config`, written by libgit2 as part of the remote and read back by `git.rs`'s `parse_managed_remote` for the heartbeat — which is *exactly* where the desktop app keeps it, and the same place self-host's `deploy/github-sync.sh` keeps it. So "no secret file of the shim's own" is already true, and `git credential approve` would not remove a copy, it would add a second one: the same token in the machine's global git credential store as well as in the folder that needs it. Two further reasons it is not done rather than merely postponed. The command is `system git` by definition, and shelling out to it is the dependency this crate deliberately avoids (`gitwrite.rs` argues it at length: a spawn depends on `PATH`, and a Windows "Git from Git Bash only" install fails silently) — and it would be reached from a *shim*, whose whole reason to exist is not depending on what the machine happens to have.
